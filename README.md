# Clothes Advisor

REST-сервис для подбора одежды из личного гардероба с учётом погоды. Учебный проект по [курсу высоконагруженных систем](https://github.com/Discipliny/highload_systems).

- **USER** загружает вещи и фотографии, составляет образы вручную или через AI.
- **STYLIST** с разрешения владельца просматривает гардероб, создаёт образы и оценивает чужие.
- **ADMIN** управляет ролями и блокировками, просматривает и удаляет фотографии и образы.

Стек: Kotlin, Spring Boot, PostgreSQL, Spring Data JDBC/R2DBC, Flyway, Yandex Object Storage и OpenAI. В ЛР2 API гардероба находится в `wardrobe-service`, AI-подбор — в `recommendation-service`, пользователи, их история и разрешения стилистам — в `account-service` с R2DBC и отдельной БД. Gateway направляет запросы аккаунтов в account; wardrobe проверяет пользователей и разрешения через AccountClient. Пакеты разделены по техническим слоям, внутри — по предметным областям.

Несекретные настройки OpenAPI и сервисов хранятся в `config-repository/` и выдаются локальным Config Server. Compose монтирует каталог серверу только для чтения; пароли и credentials остаются в переменных окружения и secret mounts. При недоступном Config Server приложение не запускается. Уже запущенное приложение продолжает работать со значениями, загруженными при старте; перезапустите его, чтобы получить изменения. Config Server запускается первым, затем Eureka Discovery Server; `wardrobe-service`, `account-service` и `recommendation-service` регистрируются под своими именами. Порт Eureka доступен только внутри Compose-сети.

В этой версии нет входа и контроля доступа к API. Действующий пользователь задаётся заголовком `X-User-Id`; это не аутентификация. Приложение предназначено только для доверенного локального окружения. Проверки владельца, разрешений стилиста и другие бизнес-правила сохраняются.

## Быстрый запуск

Нужны Docker с Compose и приватный бакет Yandex Object Storage с доступом на чтение и загрузку файлов.

Если `.env` ещё нет, создайте его из примера:

```shell
cp .env.example .env
```

Заполните в `.env`:

- `S3_BUCKET` — имя приватного бакета.
- `YANDEX_SERVICE_ACCOUNT_KEY_FILE` — абсолютный путь к JSON-файлу авторизованного ключа сервисного аккаунта с правами чтения и загрузки объектов в этот бакет. Храните файл вне репозитория и контекста сборки Docker; он должен быть доступен для чтения пользователю `APP_UID`.
- `DB_PASSWORD` — пароль PostgreSQL гардероба.
- `ACCOUNT_DB_PASSWORD` — отдельный пароль PostgreSQL аккаунтов. Оба значения из примера подходят только для локального запуска.
- `APP_UID` — результат `id -u`; `CHATGPT_CREDENTIALS_DIR` и `OPENAI_MODEL` — настройки [подключения ChatGPT](#ai-подбор).

Профиль `local` уже включён в примере. Он создаёт аккаунты `user`, `stylist`, `admin`; повторный запуск не меняет существующие аккаунты. Регистрации через API нет.

Account запускается с отдельным PostgreSQL и томом `account-postgres-data`; его HTTP и БД доступны только внутри Compose. Профиль `local` создаёт демонстрационные аккаунты только в account до готовности сервиса; Gateway ждёт его healthcheck.

При обновлении существующей установки сначала остановите запись и выполните [перенос аккаунтов и сверку манифестов](docs/lab2/account-data-transfer.md). Только после проверки запускайте новую wardrobe: Flyway V11 автоматически снимает пять внешних ключей на старую копию аккаунтов. Не запускайте новый образ wardrobe до переноса. Старые таблицы и история сохраняются; после новых записей возвращать старого писателя без обратной сверки нельзя.

```shell
docker compose up --build -d
```

После старта Gateway проверьте `curl http://127.0.0.1:8080/actuator/health`: ожидаемый ответ — `{"status":"UP"}`. Регистрация в Eureka распространяется асинхронно; первые API-запросы могут вернуть 503 до обновления реестра. Единственный HTTP-порт доступен только с локального компьютера; его можно изменить через `APP_PORT`. Порт БД также доступен локально и настраивается через `DB_PORT`. Ссылки ниже рассчитаны на порт 8080.

Остановка — `docker compose down`. Данные PostgreSQL сохраняются в именованном томе. `.env` с паролями и ключами не коммитится.

Миграции не исправляют старые данные автоматически. Если в существующей БД есть названия длиннее 300 символов или логины, цвет и материал длиннее 100, новые ограничения остановят запуск: такие записи нужно сначала проверить и исправить вручную.

Фотографии передаются в [HTTP API Yandex Object Storage](https://yandex.cloud/ru/docs/storage/api-ref/authentication) с IAM-токеном, без AWS SDK. Создайте [авторизованный ключ сервисного аккаунта](https://yandex.cloud/ru/docs/iam/operations/authorized-key/create) и укажите путь к JSON-файлу в `YANDEX_SERVICE_ACCOUNT_KEY_FILE`. Compose монтирует его как секрет только для чтения в `/run/secrets/yandex-service-account-key`; в образ ключ не попадает.

Приложение получает IAM-токен по подписанному JWT при первом обращении к Object Storage и обновляет его автоматически до истечения срока. При временном сбое IAM используется только ещё действующий токен; повторная попытка — через 30 секунд. Если действующий токен получить не удалось, загрузка фотографий и получение их содержимого возвращают 503. Работа с метаданными фотографий токена не требует. Запуск приложения не обращается к IAM; ключ перечитывается при каждом обновлении токена.

## Демонстрационный интерфейс

Откройте [Clothes Advisor](http://127.0.0.1:8080/) и выберите тестового пользователя. В интерфейсе доступны гардероб с фотографиями, образы и история оценок. Владелец выдаёт доступ стилистам и запускает AI-подбор; стилист работает с клиентами, создаёт образы, ставит и отменяет оценки; администратор меняет роли и статусы, просматривает и удаляет фотографии и образы пользователей.

Интерфейс находится в `frontend/public` и поставляется отдельным контейнером Caddy, без Node.js и сборщика. Общий запуск через Compose не изменился; в JAR backend статики больше нет. Для независимой пересборки: `docker compose up -d --build --no-deps frontend`.

При локальном запуске backend через `bootRun` запустите frontend отдельно. Gateway по умолчанию ищет его на порту 8082:

```shell
docker build -t clothes-advisor-frontend ./frontend
docker run --rm -p 127.0.0.1:8082:8080 clothes-advisor-frontend
```

Выбор пользователя хранится только в памяти вкладки; при переключении прежние данные очищаются. AI-подбор доступен аккаунту `user` при настроенном подключении ChatGPT.

## API

Сначала получите ID тестового пользователя:

```shell
curl http://127.0.0.1:8080/api/admin/users
```

Затем передавайте его в запросах, где нужен действующий пользователь:

```shell
curl http://127.0.0.1:8080/api/wardrobe/items -H 'X-User-Id: 1'
curl http://127.0.0.1:8080/api/wardrobe/items \
  -H 'X-User-Id: 1' -H 'Content-Type: application/json' \
  -d '{"name":"Рубашка","categoryId":1,"color":"Белый","material":"Хлопок"}'
```

Замените `1` фактическим ID из списка. Общий [Swagger UI](http://127.0.0.1:8080/swagger-ui/index.html) на Gateway предлагает две спецификации: **Account** — аккаунты и разрешения, **Wardrobe** — гардероб, фотографии и образы (выбрана по умолчанию). JSON доступен отдельно для [Account](http://127.0.0.1:8080/v3/api-docs/account) и [Wardrobe](http://127.0.0.1:8080/v3/api-docs/wardrobe). Документация Wardrobe включена только с профилем `local`; запросы из UI идут через текущий адрес Gateway, включая выбранный порт. Ссылка на документацию также есть на стартовой странице интерфейса.

Маршруты и бизнес-правила описаны в [требованиях](docs/requirements.md). Заголовок `X-User-Id` показывается в Swagger только для методов, которым нужен действующий пользователь; глобальной схемы Bearer нет.

## AI-подбор

Локальная интеграция использует личную подписку ChatGPT и доступна аккаунту `user`. API-ключ и автоматический переход на платный API не используются. В настройках ChatGPT Usage отключите дополнительные кредиты для подключения.

Вход выполняется отдельной локальной утилитой, которая не входит в этот репозиторий. Приложению нужны созданные ею `registration.json` и `credentials.json`:

- `CHATGPT_CREDENTIALS_DIR` — абсолютный путь к каталогу этих файлов вне репозитория. Процессу приложения нужен доступ на чтение файлов через ОС; рекомендуется ограничить доступ к credentials своей учётной записью.
- `OPENAI_MODEL` — доступная аккаунту модель с поддержкой изображений и структурированного ответа.

Подключение уже включено в `compose.yaml`; команда запуска та же: `docker compose up --build -d`. Каталог должен существовать до запуска: он монтируется только в `recommendation-service`, в `/run/chatgpt`, для чтения. Контейнер работает без root, с UID владельца файлов из `APP_UID`. Wardrobe не получает credentials ChatGPT: он читает фотографии из S3 и отправляет кандидатов recommendation через Feign и Eureka.

Если нужен отдельный PKCS12 для OpenAI, положите его в тот же каталог и задайте `CHATGPT_TRUST_STORE=/run/chatgpt/<имя файла>`; пароль хранилища — `changeit`. Иначе оставьте переменную пустой. Это доверие применяется только к клиенту OpenAI.

Без действующего подключения или при недоступном recommendation AI возвращает 503; остальные функции работают. Проверка данных и чтение фотографий выполняются до обращения к recommendation; при ошибке образ не сохраняется. Для запуска без AI можно указать пустой каталог и оставить `OPENAI_MODEL` пустым. После истечения токена нужен повторный вход через утилиту, перезапуск контейнера не требуется. OAuth-токены не храните в `.env` или Git.

## Сборка и тесты

Для сборки нужен JDK 25, для интеграционных тестов — работающий Docker. Каждый backend-сервис имеет собственный `settings.gradle.kts` и собирается без Gradle-файлов остальных сервисов. Wrapper общий; команды выполняются из корня репозитория:

```shell
./gradlew -p wardrobe-service bootJar       # независимая сборка wardrobe
./gradlew -p account-service bootJar        # независимая сборка account
./gradlew -p recommendation-service bootJar # независимая сборка recommendation
./gradlew -p api-gateway bootJar            # аналогично для Gateway, Config и Eureka
./gradlew bootJar                 # JAR всех backend-сервисов через общую сборку
./gradlew test                    # unit- и интеграционные тесты
./gradlew check                   # тесты и покрытие строк ≥70%
./gradlew testCodeCoverageReport  # общий отчёт покрытия
./gradlew :wardrobe-service:transportTest # максимальный пакет изображений, отдельная JVM с heap 3 ГиБ
```

Dockerfile каждого сервиса копирует только wrapper, собственные файлы сборки и `src/main`. Корневая многомодульная сборка сохранена для общих команд, покрытия и транспортного теста между wardrobe и recommendation; в Docker она не используется. Транспортный тест запускается только из корневой сборки. Интеграционные тесты используют конфигурации из соседнего `config-repository`, а тест переноса аккаунтов — также старые миграции wardrobe; поэтому тесты запускаются из полного checkout.

Код гардероба находится в `wardrobe-service`, аккаунтов — в `account-service`, AI — в `recommendation-service`, Config Server — в `config-server`, Eureka — в `discovery-server`, единая HTTP-точка входа — в `api-gateway`. Для запуска без Docker нужны PostgreSQL и переменные окружения из `.env`: Gradle сам этот файл не читает. Сначала выполните `./gradlew :config-server:bootRun`, затем `./gradlew :discovery-server:bootRun`, `APP_PORT=8081 ./gradlew :wardrobe-service:bootRun`, `APP_PORT=8083 ./gradlew :recommendation-service:bootRun` и `./gradlew :api-gateway:bootRun`. Сервисы регистрируются в Eureka; обнаружение после запуска может занять некоторое время. Команды запускаются из корня репозитория; конкретный модуль можно указать явно: `./gradlew :wardrobe-service:test`.

Account также подключается к Config/Eureka и нужен wardrobe для запросов с пользователем: `APP_PORT=8084 ./gradlew :account-service:bootRun`. Ему нужна отдельная БД `account_db`: `DB_R2DBC_URL` — R2DBC-адрес, `DB_URL` — JDBC-адрес той же БД для Flyway, `DB_USER` и `DB_PASSWORD` — её учётные данные. При отдельном запуске account передайте в `DB_PASSWORD` значение `ACCOUNT_DB_PASSWORD`; Compose делает это автоматически. Не направляйте его на рабочую БД wardrobe.

Общий отчёт JaCoCo: `build/reports/jacoco/testCodeCoverageReport/html/index.html` и `build/reports/jacoco/testCodeCoverageReport/testCodeCoverageReport.xml`. Порог ≥70% применяется к строкам backend-модулей; классы из покрытия не исключаются. Unit-тесты сервисов используют Mockito без Spring и БД. Интеграционные тесты работают с PostgreSQL Testcontainers, готовят и проверяют данные через JDBC, очищают их после теста. HTTP-клиенты проверяются на локальных заглушках; секреты из `.env` и реальные вызовы S3/OpenAI не нужны.

Для Colima на macOS перед тестами:

```shell
export DOCKER_HOST="unix://${HOME}/.colima/default/docker.sock"
export TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE=/var/run/docker.sock
export TESTCONTAINERS_HOST_OVERRIDE=127.0.0.1
```

## Ограничения

- Погода задаётся вручную; погодного сервиса нет.
- Образы неизменяемы. Вещь из сохранённого образа удалить нельзя.
- Удаление фотографии убирает запись БД, но не файл S3. Автоочистки нет; при сбое загрузки могут остаться файлы без метаданных.
- При AI-подборе фотографии передаются OpenAI. Бакет остаётся приватным.
- Публикация в интернет не входит в ЛР1–ЛР2: прежде нужно вернуть аутентификацию и контроль доступа, настроить HTTPS и отдельно согласовать использование подключения ChatGPT.
