# Проверка ЛР3 — 5 ноября 2026

Авторизация проверена на изолированном Compose-стенде с настоящими Gateway,
account-service, wardrobe-service и двумя PostgreSQL. Сервисы использовали
Config Server и Eureka, интерфейс — собранный frontend в Caddy.
Основа проверки — `f3c4676`; исходный код приложения после проверки не менялся.

## API и данные

HTTP-сценарий прошёл 36 проверок через Gateway:

- Без JWT запросы возвращают 401. `X-User-Id` не позволяет войти или сменить владельца.
- ADMIN создаёт аккаунты; USER и STYLIST получают 403 при такой попытке.
  Ответы содержат только предусмотренные поля, без пароля и хеша.
- USER создаёт, читает, изменяет и удаляет свои вещи. Чужая вещь недоступна;
  старый номер версии даёт 409. `createdAt` сохраняется, прежний снимок остаётся в истории.
  Повтор создания с тем же `Idempotency-Key` возвращает тот же результат.
- Стилист видит вещи после выдачи доступа и теряет доступ после отзыва.
  Изменение роли и блокировка учитываются с уже выданным JWT.
  ADMIN может модерировать данные заблокированного владельца.
- Внутренние маршруты и метрики через Gateway недоступны: с действующим JWT — 403.
- В PostgreSQL находятся хеши паролей и refresh-токенов.

## Сессии

- Вход требует `X-Auth-Request: 1`; без него — 403.
- Refresh-cookie имеет `HttpOnly`, `SameSite=Strict` и `Path=/api/auth`.
  На локальном HTTP `Secure` явно отключён; значение по умолчанию в конфигурации — `true`.
- Refresh меняет cookie. Повтор использованного токена отзывает всю сессию.
- Смена пароля отзывает все refresh-сессии пользователя, выход — текущую.
  Старый пароль перестаёт работать. Уже выпущенный access JWT действует до истечения срока.
- После перезапуска account-service работают прежний JWT и текущий refresh-токен.
  Настройка первоначального ADMIN не перезаписывает его действующий пароль.

## Интерфейс и запуск

В Chromium 151.0.7922.34 пройдены семь групп проверок: создание аккаунта администратором,
назначение пароля, создание вещи пользователем, восстановление входа после перезагрузки
с ротацией cookie, отсутствие credentials в Web Storage, выход и отсутствие ошибок JS.
Проверка работала с реальными API и БД. Формы аккаунта и вещи также проверены визуально.

Собраны шесть образов; все восемь контейнеров стенда прошли healthcheck.
Закрытый RSA-ключ с правами 0600 читается непривилегированным процессом account;
у wardrobe и Gateway есть только открытый ключ. Наружу опубликованы только Gateway и Eureka.
При первом запуске до обновления реестра Eureka возможен кратковременный 503,
даже если healthcheck самого Gateway уже успешен.

## Границы проверки

Реальные S3 и OpenAI не вызывались; recommendation и обновление ChatGPT credentials
не запускались. Для ЛР3 проверялся контур авторизации, без расходования квоты AI
и изменения рабочих данных. Удалённый сервер и HTTPS в этом проходе не проверялись.

Ранее пройденные проверки неизменённого кода: 189 тестов account, 640 wardrobe,
5 Gateway, межсервисный транспортный тест и 211 frontend; production-сборка frontend.
Гонки refresh, точные границы срока и ошибки внешних зависимостей покрываются
интеграционными тестами, а не ожиданием в браузере. Команды и ссылки на тесты —
в [теории](theory.md), история этапов — в [плане](implementation.md).
