# ЛР3: авторизация

Основа — `lab2` (`d28a400`). Интеграционная ветка — `lab3`; каждый этап выполняется
в отдельной feature-ветке и сливается в `lab3`. `main`, `lab2` и тег `lab1.0` сохраняются.
Ориентир для этапа — до 1500 изменённых строк; если проверка затрагивает больше кода,
этап делится по законченным сценариям. Коммиты — Conventional Commits.

## Соответствие заданию

[Задание ЛР3](https://github.com/Discipliny/highload_systems#лабораторная-работа-3)
требует Spring Security, JWT в Authorization, роли, зависимость операций от текущего
пользователя, хеширование паролей и создание пользователей только супервайзером.
В проекте супервайзеру соответствует существующий `ADMIN`.

| Требование | Реализация | Проверка |
| --- | --- | --- |
| JWT и Spring Security | Вход в account, Resource Server в account, wardrobe и Gateway | Подпись, срок, issuer, audience, обязательный subject |
| Роли | USER, STYLIST, ADMIN; актуальные права из account | Матрица разрешённых и запрещённых операций |
| Действующий пользователь | ID из проверенного JWT вместо X-User-Id | Подмена заголовка не меняет владельца |
| Хеши паролей | Spring PasswordEncoder; пароль только во входящем DTO | Проверка БД и отсутствия секрета в ответах |
| Создание супервайзером | POST /api/admin/users только для активного ADMIN | USER/STYLIST получают 403, анонимный запрос — 401 |

## Границы решения

- `account-service` проверяет пароль и подписывает JWT. Закрытый RSA-ключ доступен
  только account. Gateway и wardrobe получают открытый ключ, без права выпускать токены.
- Проверяем RS256, issuer, audience, срок действия и положительный числовой subject.
  Подпись проверяют библиотеки Spring Security/Nimbus; собственной криптографии нет.
- Роль и блокировка проверяются по текущим данным account, а не по устаревшему claim.
  Gateway проверяет аутентификацию; предметные разрешения остаются в сервисах.
- HTTP API больше не принимает `X-User-Id` как доказательство личности.
  Gateway удаляет этот заголовок, сервисы определяют пользователя из SecurityContext.
- Приватные внутренние API account/recommendation сохраняют сетевую границу ЛР2:
  не маршрутизируются через Gateway и не публикуют порт. Это не mTLS и не защита
  от компрометации доверенного контейнера. Межсервисную идентификацию не выдаём
  за уже реализованную возможность.
- Чтение метрик account/wardrobe остаётся доступным во внутренней сети, независимо
  от работоспособности БД. Gateway не публикует эти маршруты. Это сохраняет мониторинг ЛР2.
- Существующие транзакции JDBC/R2DBC, версии, история, идемпотентность, проверки
  перед/после S3 и правила хранения сохраняются. Внешние вызовы — вне транзакций.
- Access token действует 15 минут, без refresh token. Целевой интерфейс хранит его
  в памяти вкладки; перезагрузка страницы требует повторного входа.
- Первоначальный ADMIN: логин и пароль из окружения, без общего пароля по умолчанию.
  Запуск не должен перезаписывать действующий пароль или повышать роль существующего USER.
  Credentials читаются буквально из `APP_BOOTSTRAP_ADMIN_LOGIN/PASSWORD`, без SpEL
  и подстановок Spring. Через Config Server эти секреты не передаются.
- OAuth-подключение ChatGPT независимо от входа в наше приложение и не меняется.

JWT и защищённые чтения выделены отдельно от административных операций:
их тесты проверяют разные границы. До завершения этапа 07 промежуточная ветка не является
готовым обновлением рабочего стенда. Публикация и изменение удалённого сервера
не входят в автоматические действия этой лабораторной.

## HTTP-контракты

Новые операции:

| Маршрут | Кто вызывает | Данные/результат |
| --- | --- | --- |
| POST /api/auth/login | Без токена | login, password → accessToken, tokenType=Bearer, expiresIn |
| GET /api/auth/me | Активный пользователь | id, login, role; без пароля и хеша |
| POST /api/admin/users | ADMIN | login, password, role → карточка; 201 |
| PUT /api/admin/users/{id}/password | ADMIN | password, version → карточка; конфликт версии 409 |
| GET /api/stylists | USER | Активные стилисты: id/login, page/size ≤ 50 |

Последний маршрут заменяет чтение всей административной базы ради выбора стилиста.
Стилист получает имя клиента из существующего списка разрешённых клиентов.
Существующие GET/PUT `/api/admin/users` становятся административными.

Ошибки: 400 — неверный формат; 401 — нет действующего токена или неверные данные
входа; 403 — недостаточно текущих прав/аккаунт заблокирован; 409 — конфликт логина
или версии; 503 — account недоступен. Ошибка входа не раскрывает наличие логина.
Пароли, токены и ключи не записываются в логи/документацию/репозиторий.

## Критерии завершения

- Все публичные бизнес-операции требуют действующего JWT; вход и статические
  ресурсы доступны без него. Чтение документации и health не раскрывает данные пользователей.
- Без токена и при подмене X-User-Id нельзя читать/менять чужие данные или создавать пользователя.
- Изменение роли/блокировка учитываются следующим бизнес-запросом; прежние гарантии
  разрешённой операции и повторной проверки после скачивания фотографии сохранены.
- Пароли новых пользователей хешируются. Старые заглушки не становятся паролями.
  Начальная настройка не меняет уже заданные credentials при перезапуске.
- Пройдены затронутые unit/integration tests, независимое ревью и сквозная проверка.
- В [теории](theory.md) явно разделены реализованные возможности и ограничения;
  есть путь от каждого требования до кода и команды демонстрации.
