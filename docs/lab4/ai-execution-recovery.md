# Восстановление подключения AI

Подключитесь к БД recommendation под учётной записью оператора. Проверьте состояние слота.

```sql
SELECT state, mode, phase, execution_id, request_month, request_id, started_at
FROM ai_execution_slot WHERE connection_id = 'personal';
```

Для разбора RUNNING или PAUSED остановите все реплики recommendation-service и проверьте, что прежний процесс завершился. Время с момента захвата слота не доказывает остановку владельца. Запишите показанный UUID. В командах psql замените значение переменной этим UUID.

```sql
\set execution 'UUID-слота'
SELECT recover_ai_execution(:'execution'::uuid);
```

Запускайте `recover_ai_execution` для RUNNING. В PREPARING она освобождает слот и возвращает фоновую работу в очередь, где worker проверит исходный deadline. В CALL_STARTED она ставит подключение на паузу. Для фонового задания в той же транзакции фиксируются UNKNOWN и событие результата. Синхронный вызов оставляет PAUSED без фонового задания. Значение false означает, что переданный UUID или состояние больше не совпадают. Повторно прочитайте слот перед дальнейшими действиями.

После разбора UNKNOWN и отдельного решения разрешить **будущие** вызовы выполните для PAUSED следующую команду. Для ASYNC она также фиксирует время ручного разбора. Провайдер может продолжать ранее начатую работу даже после остановки локальных процессов.

```sql
SELECT resume_ai_execution(:'execution'::uuid);
```

Проверьте состояние FREE и запустите реплики. Прежнее задание сохранит UNKNOWN и свой event ID. Для обслуживания можно выключить опрос очереди свойством `app.ai-worker.enabled=false`. Синхронный маршрут продолжает использовать постоянный слот, поэтому для ручного разбора требуется остановка реплик.
