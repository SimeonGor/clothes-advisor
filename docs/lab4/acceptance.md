## Демонстрация в двух браузерных сессиях

1. Подготовьте отдельные учётные записи USER и STYLIST, несколько тестовых вещей с PNG/JPEG и разрешение стилисту на этот гардероб. Для сценария подбора понадобится личное тестовое подключение либо стенд с имитатором. Запустите стек по README. Проверьте `docker compose ps -a`: БД и брокеры готовы, `kafka-provision` завершился с кодом 0. Откройте приложение в разных профилях браузера. [Подготовка и запуск](../../README.md#быстрый-запуск)
2. В USER откройте «Запросы стилисту» → «Новый запрос». В STYLIST откройте «Уведомления», перейдите к запросу клиента и ответьте образом. В USER откройте ответ. Нажмите «Отметить прочитанным» и обновите страницу. Проверьте счётчик и сохранность `readAt`. [Последовательность](diagrams/stylist-request.svg)
3. В USER запустите подбор образа. В сетевой панели сохраните его `Location`, дождитесь конечного состояния в «Мои AI-задания» и перейдите по `result.url`. Повторите для замены одной вещи и для капсулы. Для замены понадобятся исходный образ и подходящий новый кандидат. С теми же телом и ключом повторите один POST через Swagger. Сравните оба jobId и количество созданных ресурсов. [HTTP и примеры ответов](api.md)
4. Добавьте фотографию к вещи и получите оригинал через публичный API гардероба. Сравните SHA-256 исходного и загруженного файлов. Снимите доступ стилисту и повторите скачивание из его сессии. Открытая ранее карточка сохраняет только ссылку. [Граница доступа к файлам](api.md#внутренние-файлы-и-проверка-входа)
5. На изолированном стенде проследите повтор доставки по исходному eventId, задержку при отказе брокера и состояние после восстановления. Для прерывания worker в фазе `CALL_STARTED` используйте имитатор с задержкой и счётчиком. После разбора сравните число обращений с исходным. [Команды и признаки отказов](operations.md) · [Разбор слота](ai-execution-recovery.md)

## Повторяемые проверки

В корне checkout с JDK 25 и Docker выполните сервисные и транспортные тесты. Отчёты JUnit сохраняются в `<module>/build/test-results`. В каталоге frontend выполните установку по lock-файлу, проверки интерфейса и сборку.

~~~sh
./gradlew test
./gradlew :wardrobe-service:transportTest
python3 -m unittest discover -s infra/kafka/tests -v
(cd frontend && npm ci && npm test && npm run build)
~~~

В профиле `local` один Swagger UI показывает Account, Wardrobe и Notification. Следующие проверки через Gateway возвращают соответственно число публичных маршрутов v2 и список маршрутов уведомлений.

~~~sh
curl -fsS http://127.0.0.1:8080/v3/api-docs/wardrobe | jq '[.paths | keys[] | select(startswith("/api/v2/"))] | length'
curl -fsS http://127.0.0.1:8080/v3/api-docs/notification | jq '.paths | keys'
~~~

Настоящий вызов ChatGPT проверяется отдельно с согласованным подключением. Для smoke Yandex Object Storage нужны согласованный тестовый бакет, IAM-ключ и тестовое изображение. Локальный имитатор позволяет воспроизвести потерю ответа и проверить число попыток. Проверки имитатора и реального провайдера записываются раздельно.

## Итоговый прогон

Проверка 10 ноября 2026 года проходила на отдельном Compose-стенде с тремя брокерами Kafka и отдельными PostgreSQL для пяти бизнес-сервисов. Для фотографий, IAM и ответа модели использовались локальные HTTP-имитаторы. Все пользовательские операции шли через Gateway.

| Сценарий | Наблюдение |
| --- | --- |
| Образ, замена вещи, капсула | Три POST v2 вернули `202`. Повтор каждого с тем же ключом вернул исходный jobId. По завершении все три ресурса открылись по HTTP, подтверждения применения сохранились в recommendation, владельцу пришло по уведомлению. |
| Запрос стилисту | После выдачи доступа стилист получил запрос, ответил образом из вещей клиента. Владелец прочитал уведомление. Повтор отметки сохранил прежний readAt, попытка другого пользователя дала `404`. |
| Обрыв ответа провайдера | Для старого маршрута повреждённый поток дал `502`, затем `503` до разбора. Для фонового задания исполнителя остановили после первого обращения к модели. После восстановления обе БД зафиксировали `UNKNOWN`; повтор с прежним ключом оставил счётчик провайдера равным одному. |
| Потеря брокеров | При остановке одного узла три партиции сохранили по две синхронные реплики и доставили событие. При остановке трёх отзыв доступа завершился с `204`, а событие осталось в outbox. После восстановления кворума и перезапуска одного узла доставлен тот же eventId, получатель получил одну строку. |
| Остановка consumer и пауза БД | В обоих опытах lag группы уведомлений вырос до 1 и после восстановления вернулся к 0. Две дополнительные публикации одного конверта увеличили счётчик дублей на 2, число уведомлений для этого события осталось равным 1. Событие с неподдерживаемой версией попало в карантин. |
| Смена аккаунта в браузере | В Chromium получили ответ на запрос задания USER и задержали его доставку в страницу до входа STYLIST. В новой сессии сохранился экран клиентов. Запросов прежнего задания и повторных POST от новой сессии было 0. |
| История и переходы из уведомлений | После обновления страницы выбранное задание перешло из очереди в готовые одновременно в строке и подробностях. По ссылке открылся сохранённый образ. После отзыва доступа переход стилиста по старому уведомлению дал `404` и сообщение об отсутствии доступа. |

Финальный `docker compose up -d --build --wait` завершился успешно с тестовыми адресами внешних провайдеров. На хост опубликованы только Gateway и Eureka, оба слушают loopback. Через Gateway открыт сохранённый образ и проверены три группы OpenAPI профиля `local`, включая тип `integer/int64` заголовка `X-Total-Count` у уведомлений.

В Gradle прошли 1044 проверки пяти сервисов, включая транспортный тест с 20 фотографиями по 10 МБ. В frontend прошли сборка и 226 тестов. Из-за нагрузки на локальную машину финальный набор Vitest запускали с одним worker и таймаутом 20 секунд на тест. Для разбора сбоев и сравнения позиций Kafka используйте [операторский сценарий](operations.md).
