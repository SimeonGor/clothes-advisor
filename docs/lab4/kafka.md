# Kafka: запуск и проверка

В Compose добавлены три узла Apache Kafka 4.1.2. Каждый выполняет роли broker/controller KRaft; ZooKeeper не нужен. Образ закреплён по digest, данные каждого узла находятся в отдельном томе. Это учебный кластер на одном хосте, без защиты от отказа самого Docker-хоста.

Wardrobe публикует запросы подбора из локального outbox в `ai-selection.requests`. Recommendation сохраняет полученную команду в PostgreSQL перед подтверждением Kafka. [Контракты семи топиков](messaging.md)

## Подготовка

Нужны Python 3, OpenSSL и Docker Compose 2.20.3+. Один раз подготовьте отдельный каталог вне репозитория; родитель уже должен существовать:

```shell
mkdir -p "$HOME/.config/clothes-advisor"
python3 infra/kafka/prepare.py --secrets-dir "$HOME/.config/clothes-advisor/kafka"
```

Укажите его абсолютный путь в `.env` как `KAFKA_SECRETS_DIR`. Внешний каталог закрыт для других пользователей хоста. Подкаталоги монтируются только нужным контейнерам, read-only; файлы читаются непривилегированным UID 1000 образа Kafka. CA private key остаётся на хосте. Не переносите каталог в Git или контекст сборки.

Повтор prepare проверяет целостность и срок сертификатов, сохраняя cluster ID и credentials. Частичное или изменённое состояние отклоняется. Генерация нового каталога с прежними томами не является восстановлением или ротацией; Kafka отвергнет несовпадающий cluster ID. Для обновления credentials и сертификатов нужен отдельный согласованный порядок, автоматической ротации здесь нет.

Для сбора lag команда подготовки также создаёт соседний каталог `<каталог Kafka>.monitor`. На уже работающем стенде повторите её с исходным каталогом. Только `kafka-metrics` монтирует сертификат `CN=kafka-monitor`, его ключ и публичный CA. Клиент подключается по mTLS к внутреннему listener 9094. Provisioning выдаёт только `Describe` на конкретные группы и топики из `topology.tsv`; читать сообщения или записывать offsets клиент не может. Внутренний порт на хост не публикуется.

Каждые 30 секунд exporter сравнивает конец лога с сохранённым offset. У остановленной группы отставание остаётся видимым, пока Kafka хранит её offsets. Никогда не зафиксированные партиции не включаются в сумму. Основной Alloy принимает логи и трассы независимо от старта брокеров и сборщика Kafka.

## Запуск

Полное приложение поднимается обычным `docker compose up --build -d`. Для отдельного кластера используйте тот же файл и другой project name; так тесты не затронут тома приложения:

```shell
export KAFKA_SECRETS_DIR="$HOME/.config/clothes-advisor/kafka"
docker compose -p ca-kafka-check -f infra/kafka/compose.yaml up -d
docker compose -p ca-kafka-check -f infra/kafka/compose.yaml ps -a
docker compose -p ca-kafka-check -f infra/kafka/compose.yaml logs --tail 50 kafka-provision
```

Успешный старт: три healthy-брокера, kafka-provision завершился с кодом 0. Он создаёт топики и ACL после готовности кворума. Повтор не удаляет данные; несовместимые параметры существующего топика приводят к ошибке.

В примере `ca-kafka-check` заменяйте на имя нужного проекта во всех дальнейших командах. Завершение без удаления данных:

```shell
docker compose -p ca-kafka-check -f infra/kafka/compose.yaml down
```

Не используйте `down -v`, если данные нужно сохранить. Каталог credentials и тома относятся к одному кластеру; копирование одних credentials само по себе не восстанавливает сообщения.

## Сеть и доступ

Kafka-порты на хост не публикуются. Сеть `kafka` внутренняя; Gateway и frontend к ней не подключены. Клиентский listener 9092 использует SCRAM-SHA-512 поверх TLS. Межброкерный 9094 и controller 9093 используют mTLS с отдельным сертификатом каждого узла и проверкой имени.

Bootstrap admin применяется только для инициализации. Account, wardrobe, recommendation и notification имеют разные identities и права на точные топики и consumer groups. Сервис не может читать чужую группу или публиковать в чужой топик. Отсутствие ACL означает запрет. Root-доступ к Docker-хосту находится вне этой границы доверия.

## Настройки клиентов

При запуске через Compose четыре сервиса загружают настройки Kafka из своего каталога в `config-repository`. Account публикует события, notification их читает, wardrobe и recommendation совмещают обе роли. Там задаются адреса брокеров, параметры producer и consumer, имена групп. При смене имени группы проверьте её ACL в [топологии](../../infra/kafka/topology.tsv).

Каждый сервис получает свой файл `/run/kafka-client/client.properties` только для чтения. Из него приложение берёт параметры входа SCRAM (`sasl.jaas.config`) и доверенный CA (`ssl.truststore.certificates`). Этот же файл подходит для Kafka CLI. Конфигурация самих брокеров и настройки мониторинга находятся в `infra/kafka` и `infra/observability`.

Чтобы изменить число записей за один вызов `poll()` у notification, поменяйте `spring.kafka.consumer.max-poll-records` в [конфигурации сервиса](../../config-repository/notification-service/application.yml). Затем перезапустите только consumer и проверьте значение в журнале нового запуска:

```shell
docker compose restart notification-service
started=$(docker inspect --format '{{.State.StartedAt}}' "$(docker compose ps -q notification-service)")
docker compose logs --since "$started" notification-service | grep -F 'max.poll.records ='
```

Config Server читает примонтированный каталог. Перезапуск клиента применяет новое значение с тем же образом.

На отдельном Compose-стенде после изменения лимита с `5` на `3` Kafka consumer вывел новое значение и снова получил партиции группы `notification-service.events`. ID контейнера и образа совпали до и после перезапуска. В каждом запуске событие из outbox сервиса account дошло до базы уведомлений ровно один раз. После второго события подтверждённый offset совпал с концом партиции (lag 0).

## Обновление конфигурации через Kafka

Config Server каждые две секунды сверяет содержимое локальных файлов в каталогах `wardrobe-service` и `recommendation-service`. При изменении YAML он отправляет в `config.refresh.events` событие Spring Cloud Bus с именем сервиса. Каждый его экземпляр читает топик в собственной Kafka-группе и запрашивает свежие значения у Config Server. При временной ошибке запроса клиент повторяет его через пять секунд. Текст промпта и учётные данные в сообщение не входят.

Для существующего кластера запустите `prepare.py` с прежним `KAFKA_SECRETS_DIR`, затем `docker compose run --rm kafka-provision`. Первый шаг выпускает сертификат `CN=config-server` в соседний каталог `.config-server`, второй создаёт топик и ACL. Затем обновите сервисы обычной командой `docker compose up --build -d`.

Для проверки измените `app.openai.prompt.version` и `text` в [YAML подбора](../../config-repository/recommendation-service/application.yml) и сохраните файл. Следующий запрос после применения события использует новый промпт. Wardrobe тем же способом принимает изменения таймаутов и Circuit Breaker из [своего YAML](../../config-repository/wardrobe-service/application.yml). Параметры подключения к Kafka по-прежнему задаются при старте.

На изолированном стенде две реплики recommendation отправили в локальный имитатор OpenAI исходный текст версии 6, затем текст версии 7. При попытке установить версию 0 обе сохранили версию 7, а после восстановления файла обе снова отправили версию 6. Проверка сравнивала поле `instructions` в HTTP-запросе с полным текстом из YAML. Контейнеры и процессы не перезапускались.

## Доставка и хранение

- На топик: 3 партиции, replication factor 3, min.insync.replicas=2, retention 7 суток.
- Producer: acks=all и idempotence. Consumer: без автоматического commit offset.
- Автоматическое создание топиков и выбор несинхронной реплики лидером отключены.
- При отказе одного брокера запись может продолжаться после выбора лидеров. При двух недоступных брокерах подтверждённой записи не ожидаем.

Kafka retention — срок доставки сообщений, а не политика хранения AI-запросов PostgreSQL. Дубли после повторной публикации outbox по-прежнему возможны; бизнес-дедупликация остаётся обязательной.

## Ресурсы и проверки

Стартовый heap брокера 256–512 МиБ, служебных CLI — до 256 МиБ. Потребление процесса включает память сверх heap. На Docker с 4 ГиБ RAM и 2 CPU три брокера во время проверки потребляли 401, 416 и 376 МиБ — суммарно около 1,2 ГиБ. Это выборочный замер, не максимальное потребление. Достаточность 4 ГиБ для всего приложения с Kafka пока не подтверждена.

Скриптовые проверки без Docker:

```shell
python3 -m unittest discover -s infra/kafka/tests -v
```

Проверено 6 ноября 2026 в отдельном Compose-проекте на arm64:

- 10 скриптовых тестов прошли; первая подготовка и повтор не меняют существующие ключи/cluster ID, несовместимое состояние отклоняется.
- Три узла запущены; семь топиков, 21 партиция, RF=3 и ISR=3. Проверены все восемь направлений публикации/чтения из topology.tsv.
- Чужой топик/группа, неверный пароль и plaintext отклонены. TLS отвергает недоверенный CA и неправильное имя; внутренние listeners не принимают клиента без сертификата. Пароли, закрытые ключи и SCRAM derived secrets в логах не обнаружены.
- Повтор provisioning сохранил ACL. С одним остановленным брокером acks=all работает, с двумя запись не подтверждается. После восстановления ISR=3, подтверждённые сообщения доступны.
- Полный перезапуск тестового кластера с прежними томами сохранил cluster ID и сообщения. Тома не очищались.
- Корневой Compose проверен с тестовым env-файлом; реальный Config Server отдаёт новые несекретные параметры трём сервисам. Весь прикладной стенд, S3 и OpenAI в эту проверку не включались.

Kafka-скрипты новые, поэтому их тестовые сценарии добавлены впервые. Существующая логика и зависимости приложения на этом этапе не менялись.

Основания: [KRaft](https://kafka.apache.org/41/operations/kraft/), [SCRAM](https://kafka.apache.org/41/security/authentication-using-sasl/), [TLS](https://kafka.apache.org/41/security/encryption-and-authentication-using-ssl/), [ACL](https://kafka.apache.org/41/security/authorization-and-acls/). Для control-plane выбран mTLS, учитывая известную проблему первого старта SCRAM-кворума [KAFKA-15513](https://issues.apache.org/jira/browse/KAFKA-15513).
