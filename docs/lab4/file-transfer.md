# Перенос старых фотографий в file_db

В окно обслуживания оператор назначает UUID прежним фотографиям в wardrobe и переносит их метаданные в `file_object`. Публичный `photoId`, ID вещи, ключ и содержимое объекта S3 сохраняются. [Миграция V22](../../wardrobe-service/src/main/resources/db/migration/V22__add_photo_file_id.sql) добавляет nullable UUID с ограничением UNIQUE. Старые версии wardrobe могут по-прежнему создавать фотографии без UUID.

## Подготовка

1. Выделите окно обслуживания. Закройте внешний трафик wardrobe, остановите фоновые и ручные записи в обе БД и в бакет. Дождитесь завершения уже начатых запросов и транзакций, остановите все прежние экземпляры wardrobe. Сохраняйте этот режим до проверки и переключения писателей. Блокировки в скрипте действуют только в пределах каждой локальной транзакции.
2. Проверьте адреса и назначение двух отдельных libpq-подключений. В примере `service=wardrobe-source` указывает на БД wardrobe, а `service=file-target` на БД file-service. Используйте административные роли с доступом ко всем строкам, храните пароли в защищённом файле libpq. Для PostgreSQL 18 нужны клиентские `pg_dump`, `pg_restore`, `psql` той же основной версии, Bash и приватный каталог вне репозитория с местом для дампов и двух копий манифеста.
3. Сохраните эталонные байты старой фотографии с известным числовым `photoId` и точным ключом, например `старое/пальто.jpg`. Получите их проверенным прежним путём чтения из того же бакета. Для репетиции заранее положите синтетическое изображение по такому ключу в локальное тестовое хранилище и занесите его метаданные в тестовую wardrobe. Во время переноса файловый PUT не требуется.

Выполняйте команды в одной Bash-сессии из корня репозитория. Замените путь к каталогу и имена подключений своими. Сообщения об ошибках могут содержать отдельные метаданные, держите логи вместе с дампами.

```bash
set -euo pipefail
umask 077
work=$(mktemp -d /absolute/private/backup-dir/photo-transfer.XXXXXX)
src='service=wardrobe-source'
dst='service=file-target'
tool=ops/file-transfer/transfer.sh
pg_dump --format=custom --file="$work/wardrobe.dump" "$src"
pg_dump --format=custom --file="$work/file.dump" "$dst"
pg_restore --list "$work/wardrobe.dump" > "$work/wardrobe.toc"
pg_restore --list "$work/file.dump" > "$work/file.toc"
```

Проверьте возможность восстановления обеих копий в изолированной среде. Примените wardrobe V22 из сборки 05b либо задайте Flyway `target=22` (`SPRING_FLYWAY_TARGET=22` для Spring Boot) на подготовительном запуске. Примените file V1, затем остановите приложения. Проверьте успешные версии в `public.flyway_schema_history` на каждом подключении. Оставьте wardrobe на V22 до завершения импорта, поскольку скрипт читает удаляемый в V23 столбец `s3_key`. Проверьте доступ file-service к исходному S3 endpoint и бакету. [Схема file-service](../../file-service/src/main/resources/db/migration/V1__create_file_object.sql)

## Назначение UUID и экспорт

```bash
bash "$tool" prepare "$src" 2> "$work/prepare.log"
bash "$tool" export "$src" "$work/photos.copy" 2> "$work/export.log"
wc -l < "$work/photos.copy"
```

`prepare` берёт блокировку от писателей, проверяет все строки на JPEG/PNG и размер от 1 до 10 000 000 байт включительно. После успешной проверки он заполняет только пустые `file_id` и фиксирует транзакцию. При несовместимых данных разберите указанную фотографию, сохраните первоначальные значения для разбора и согласуйте исправление до повтора.

`export` создаёт новый файл. Столбцы по порядку — `photoId`, ID вещи, `file_id`, точный `s3_key`, MIME, размер и исходный `created_at` в UTC. Формат — PostgreSQL COPY text в UTF-8 без заголовка, одна физическая строка на фото в порядке `photoId`. COPY экранирует обратную косую черту, табуляцию и переводы строк. Пустому источнику соответствует пустой файл. Сохраните его вне репозитория с резервными копиями.

## Импорт и сверка

```bash
bash "$tool" import "$src" "$dst" "$work/photos.copy" 2> "$work/import.log"
```

Скрипт заново выгружает все строки из wardrobe и побайтово сравнивает их с сохранённым файлом. Даже потеря одной полной строки или изменение даты при прежнем количестве строк останавливает импорт до обращения к цели. Затем скрипт загружает проверенный снимок во временную таблицу отдельным подключением к file_db. Под блокировкой он вставляет отсутствующие UUID и сверяет ключ, MIME, размер и дату для каждой исходной строки. Занятый ключ с чужим UUID, занятый UUID с другими полями или ошибка COPY прерывают всю целевую транзакцию. Строки вне исходного списка сохраняются.

## Проверка GET

Запустите file-service с целевой БД и прежним бакетом в изолированной сети, сохраняя запрет на запись. Задайте `PHOTO_ID` числовым ID эталонной фотографии, `REFERENCE` путём к эталонному файлу, `FILE_URL` внутренним адресом file-service и `NETRC` защищённым netrc с подходящей служебной учётной записью для этого хоста.

```bash
file_id=$(psql -XqAt -v ON_ERROR_STOP=1 -v photo_id="$PHOTO_ID" "$src" <<'SQL'
SELECT file_id FROM public.wardrobe_item_photo WHERE id = :'photo_id'::bigint;
SQL
)
test -n "$file_id"
status=$(curl --silent --show-error --fail --netrc-file "$NETRC" \
    --dump-header "$work/get.headers" --output "$work/get.bytes" --write-out '%{http_code}' \
    "$FILE_URL/api/files/$file_id")
test "$status" = 200
cmp "$REFERENCE" "$work/get.bytes"
```

Сверьте `Content-Type` и `Content-Length` в `get.headers` с MIME и размером исходной записи. При ответе 404 проверьте наличие прежнего объекта и конфигурацию бакета, при 503 — доступность хранилища. Сохраните доказательства сверки и результата GET до открытия записи. [Контракт GET](api.md)

## Переключение на V23

1. Выполните `prepare`, свежий `export`, полный `import` и проверку GET выше в одном окне обслуживания. Даже если перенос уже проходил на V22, старые писатели могли добавить строки без UUID. Сохраните манифест и результат сверки. При расхождении остановитесь на V22. Ограничение NOT NULL проверяет только wardrobe и не подтверждает наличие соответствующих строк в file_db.
2. Только после успешной сверки уберите подготовительное ограничение V22 и запустите новую сборку wardrobe при закрытом трафике. Flyway применит V23. Миграция одним оператором делает `file_id` обязательным и удаляет `s3_key`. При пустом UUID PostgreSQL отклонит весь оператор и сохранит прежний столбец. [Миграция V23](../../wardrobe-service/src/main/resources/db/migration/V23__require_photo_file_id.sql)
3. Через закрытый для внешнего трафика экземпляр wardrobe прочитайте список фото прежней вещи и `GET /api/wardrobe/items/{itemId}/photos/{photoId}/content` с полномочиями владельца. Сверьте числовой `photoId`, MIME, размер и байты с эталоном. Загрузите тестовое изображение через `POST /api/wardrobe/items/{itemId}/photos`, прочитайте его по возвращённому числовому ID и сравните байты с отправленными. Откройте трафик после обеих проверок.

## Прерывание и повтор

* После фиксации в wardrobe повторите `prepare`, экспортируйте в новый файл и сравните его с первым, если первый экспорт завершился. Присвоенные UUID сохраняются.
* После фиксации в file_db, в том числе при потере ответа о коммите, повторите импорт по тому же манифесту при сохранённом запрете записи. Полностью совпавшие строки пройдут сверку.
* При конфликте оставьте писателей остановленными и установите источник расхождения по дампам и манифесту. Для отмены до переключения можно вернуться к прежнему wardrobe с nullable UUID. При необходимости восстановления данных восстанавливайте согласованные резервные копии обеих БД в отдельном контуре и проверяйте их до переключения. Существующие файлы могут принадлежать другим операциям, поэтому удаление импортированных UUID списком для отката не подходит.
* Если прежний wardrobe снова принимал записи, новые фотографии могли получить пустой UUID. Для окончательного переключения повторите `prepare` и сверку по свежему манифесту под новым запретом записи.
* После V23 старый wardrobe не сможет работать без `s3_key`. При сбое закройте трафик и остановите запись. Если записей после V23 ещё не было, восстановите и проверьте согласованные резервные копии перед возвратом прежней версии. После первой записи, включая тестовую загрузку, исправьте переключение вперёд либо отдельно перенесите новые связи и точные ключи из file_db в восстановленную схему и сверьте все данные до запуска старого приложения. Восстановление только исходных дампов потеряет новые записи.

## Репетиция на PostgreSQL 18

Тест создаёт два временных кластера с отдельными Unix-сокетами, применяет миграции репозитория и удаляет кластеры по завершении. Запустите его обычным пользователем с `initdb`, `pg_ctl` и `psql` в PATH.

```bash
bash ops/file-transfer/tests/run.sh
```

Для запуска в одноразовом контейнере выполните из корня репозитория следующую команду.

```bash
docker run --rm --user postgres --entrypoint bash -v "$PWD:/repo:ro" -w /repo \
    postgres:18-alpine ops/file-transfer/tests/run.sh
```

Тест проверяет пустой источник, прежнюю форму INSERT, сохранение числовых ID и UUID при повторе после обеих фиксаций, ключи с каталогами и спецсимволами, полноту манифеста, отказ на несовместимых данных, атомарность конфликтов и сохранность посторонних файлов. Побайтовый GET проверяется отдельно с работающим file-service и S3.
