# Сервис подбора одежды — требования к ЛР1

## О проекте

Сервис помогает составлять образы из личного гардероба с учётом погоды. Пользователь загружает фотографии вещей, описывает их и выбирает погодные условия. Образ можно собрать самостоятельно, поручить стилисту или получить через OpenAI.

Приложение — монолит на Kotlin и Spring Boot. Данные хранятся в PostgreSQL, фотографии — в приватном Yandex Object Storage с доступом по S3 API. Для входа используются Spring Security и JWT.

В ЛР1 используются заранее созданные тестовые аккаунты. Регистрации, создания аккаунтов через API и интеграции с погодным сервисом нет. Реализация ведётся небольшими отдельными этапами.

В ЛР1 удаление выполняется физически — через `DELETE` строки из таблицы. История изменений и файлы S3 сохраняются, остальные зависимые записи удаляются. Вещь нельзя удалить, пока она входит хотя бы в один образ. Архивирование и восстановление отложены; правила будущего архива описаны отдельно.

## Пользователи и доступ

| Роль | Возможности |
|---|---|
| USER | Ведёт свой гардероб, создаёт и удаляет свои образы, запускает AI-подбор, выдаёт и отзывает доступ стилистам. |
| STYLIST | С разрешения владельца просматривает его гардероб и образы, создаёт образы и оценивает чужие работы. |
| ADMIN | Назначает роли, блокирует и разблокирует аккаунты. Просматривает и удаляет фотографии и образы для модерации без разрешения владельца. Не выставляет оценки. |

Разрешение выдаётся конкретному стилисту сразу на весь гардероб и все образы владельца. При отзыве стилист теряет доступ, в том числе к фотографиям, и больше не может создавать образы или менять оценки этого клиента. Прежние оценки и их история сохраняются и продолжают учитываться в счётчиках. Повторная выдача доступа не создаёт дополнительного голоса.

У аккаунта два статуса: `ACTIVE` и `BLOCKED`. Только активный пользователь может войти и выполнять защищённые операции. Блокировка действует и для ранее выданного JWT, но не удаляет данные. Менять статус может только администратор; изменение сохраняется в истории пользователя.

Пароли хранятся в виде хешей и не возвращаются в ответах. Секреты и изображения не попадают в логи или Git. Прямой доступ к публичному URL фотографии не должен позволять обойти проверку прав.

### Вход

`POST /api/auth/login` принимает логин и пароль и выдаёт access token JWT на 30 минут. Refresh-токенов нет: после истечения срока пользователь входит заново. Токен передаётся только в заголовке `Authorization: Bearer …`; серверные HTTP-сессии для входа не используются. `GET /api/auth/me` возвращает ID, логин и текущую роль пользователя, без пароля и хеша.

На каждом защищённом запросе проверяются JWT и актуальные роль и статус аккаунта из БД. Некорректный запрос возвращает 400; неверные реквизиты входа, заблокированный аккаунт или недействительный JWT — одинаковый 401 без уточнения причины; недостаточная роль — 403.

Профиль `local` создаёт отсутствующие аккаунты `user`, `stylist` и `admin` с соответствующими ролями. Пароли задаются окружением и сохраняются как BCrypt-хеши; повторный запуск не меняет существующие пароль, роль или статус. Без локального профиля аккаунты автоматически не создаются. BCrypt ограничивает пароль 72 байтами UTF-8; это ограничение действует при локальной инициализации и входе. Ключ подписи JWT также передаётся окружением, рабочего ключа по умолчанию нет.

## Гардероб и фотографии

На одной фотографии находится одна вещь. Пользователь выбирает категорию из справочника и вручную указывает характеристики. Карточку своей вещи можно создать, просмотреть, изменить и удалить.

Фотографии хранятся в приватном S3, ключи объектов и метаданные — в БД. Вещи без доступных фотографий не участвуют в AI-подборе до загрузки фото.

## Образы, погода и оценки

Пользователь задаёт температуру в °C и скорость ветра в м/с, а вид осадков выбирает из справочника. Эти условия сохраняются вместе с образом и не обновляются вслед за текущей погодой.

Стилист составляет образ из вещей клиента: клиент остаётся владельцем, а стилист — автором. Сохранённые образ, состав и погода не редактируются. Изменение состава создаёт новый образ с отдельным ID и без переноса оценок. При этом ссылки на вещи не фиксируют их прежний внешний вид: изменения характеристик и доступности фотографий видны и в старых образах.

Для AI-подбора используются существующие вещи владельца с доступными фотографиями. Сервис передаёт фотографии и описание задачи в [OpenAI](https://developers.openai.com/api/docs/guides/images-vision), перед сохранением результата повторно проверяет наличие вещей, их владельца и доступность фото. Ошибка интеграции не должна приводить к сохранению образа как успешно подобранного. Результат доступен пользователю сразу, без предварительного одобрения стилистом.

Оценивать образ может только стилист с действующим доступом к гардеробу владельца. Автор не оценивает собственную работу. У каждого стилиста один текущий голос на образ — `LIKE` или `DISLIKE`. Новая оценка заменяет текущую и сохраняет предыдущее состояние, даже если значение голоса не изменилось. Счётчики учитывают только текущие голоса.

## Удаление в ЛР1

Удаление вещи, фотографии или образа означает удаление основной строки из PostgreSQL, без перевода в архив. Отзыв доступа удаляет действующую пару из `access_grant`; прежние оценки стилиста и их история от этого не меняются.

| Что удаляется | Правило |
|---|---|
| Вещь, входящая хотя бы в один образ | Удаление запрещено. Вещь, состав образа, фото и история не меняются. |
| Вещь, не используемая в образах | Удаляются вещь и строки её фотографий. История вещи сохраняется. |
| Фотография | Удаляется строка с ключом S3 и метаданными. Вещь и состав образов остаются. |
| Образ | Удаляются образ, его состав, погода и текущие оценки. История оценок и сами вещи сохраняются. |

Файлы фотографий остаются в приватном S3 и при отдельном удалении фото, и при удалении вещи. Без действующей строки `garment_photo` сервис не выдаёт файл и не использует его для AI-подбора. Сохранение файла не означает сохранения метаданных или возможности восстановления через API. Автоматической очистки файлов и истории нет.

Удаление основной строки и её зависимостей выполняется одной транзакцией. Проверка запрета удаления используемой вещи должна работать и при одновременном создании образа; отдельной предварительной проверки в приложении недостаточно. Удаление аккаунтов, справочников и отдельных оценок не входит в ЛР1.

## Архивирование — дальнейшее развитие

Архивирование пока не реализуется. Для его последующего добавления приняты следующие правила.

При архивировании вещи её статус меняется с `ACTIVE` на `ARCHIVED`. Она исчезает из активного гардероба и больше не используется в новых ручных и AI-образах. В уже сохранённых образах вещь остаётся вместе с фотографиями и историей.

Архивирование фотографии — отдельная операция. Сам файл сохраняется в приватном S3, ключ и метаданные — в БД. Сервис не выдаёт архивное фото ни в карточке вещи, ни в старых образах и не передаёт его в AI-подбор. Сама вещь остаётся в гардеробе; если доступных фотографий больше нет, AI-подбор её не использует до загрузки нового фото.

Архивный образ сохраняет состав, погоду, оценки и историю, но недоступен для обычного просмотра, в том числе по прямому ID, и для новых оценок. Администратор сохраняет модерационный доступ. Архивирование образа не затрагивает вещи гардероба.

Архивирование не удаляет связанные записи каскадом. Автоматическая очистка историй, будущих архивов и архивных файлов S3 не предусмотрена. Отдельные операции удаления аккаунтов, справочников и оценок не вводятся. Восстановления в ЛР1 не будет; его дальнейшие правила пока не определены.

## Архитектура

[Схема монолита](architecture.png) · [исходник PlantUML](architecture.puml)

Приложение работает одним процессом и использует общую PostgreSQL. Внутри выделены пять модулей:

| Модуль | Ответственность |
|---|---|
| Пользователи и безопасность | Вход, JWT, роли, статусы аккаунтов. |
| Гардероб и фотографии | Вещи, категории, характеристики и хранение фото. |
| Образы | Авторство, владелец, состав и погодные условия. |
| Доступ и оценки | Разрешения стилистам, текущие голоса, история и счётчики. |
| AI-подбор | Обращение к OpenAI, проверка и сохранение результата. |

Модули взаимодействуют через вызовы методов. Контроллеры и DTO отделены от сервисов, моделей и репозиториев. Административные операции выполняются в тех же модулях с проверкой роли. Вызовы S3 и OpenAI проходят вне транзакций БД.

Пакеты организованы сначала по техническим слоям, затем по предметным областям: например, `model.user`, `repository.user`, `service.user`. Новые контроллеры и DTO следуют тому же правилу. Бизнес-модули на схеме описывают ответственность, а не верхний уровень пакетов.

## Организация данных

[ER-модель](domain.png) · [исходник PlantUML](domain.puml)

Схема выполнена в нотации Crow’s Foot. Таблицы и поля именуются в `snake_case`; первичные, внешние и уникальные ключи обозначены как PK, FK и UK. Это проект схемы БД, который ещё нужно согласовать с преподавателем. Ориентир — третья нормальная форма; окончательная проверка зависит от детализации характеристик вещей и метаданных фото.

ER отражает ЛР1 с физическим удалением: архивных таблиц и статуса `ARCHIVED` вещи в ней нет. Версии и таблицы `_history` сохраняются; история вещи и оценок не зависит от существования удалённой основной строки.

### Связи и справочники

- Категории хранятся в `garment_category`, виды осадков — в `precipitation_type`. Оба справочника содержат `id`, уникальный `code` и `name`. Вещь и её история ссылаются на категорию через `category_id`, не копируя название. ID и смысл используемых кодов должны оставаться стабильными. В ЛР1 начальное заполнение и изменения выполняются только миграциями; API редактирования и истории справочников нет.
- Погода хранится в `outfit_weather`: `outfit_id`, `temperature_c`, `precipitation_type_id`, `wind_speed_mps`. Ключ `outfit_id` одновременно является PK и FK. У каждого образа должна быть ровно одна погодная запись, создаваемая в той же транзакции. Сам PK/FK гарантирует лишь отсутствие второй записи.
- Состав хранится в `outfit_item` с ключом `(outfit_id, garment_id)` и полем `position`. Это ManyToMany с дополнительным полем. Происхождение образа фиксируется в `outfit.source` при создании и не зависит от последующих изменений роли автора.
- `access_grant(owner_id, stylist_id)` — обычная ManyToMany без дополнительных полей: оба столбца составляют PK и ссылаются на пользователя. Отзыв удаляет пару и прекращает действие разрешения сразу, без переноса в `access_grant_archive`. Уже поставленные оценки и их история сохраняются.
- Связи пользователя с вещами, вещи с фотографиями и пользователя с его историей — OneToMany / ManyToOne.

Начальные категории: `TOP` — Верх, `BOTTOM` — Низ, `ONE_PIECE` — Платья и комбинезоны, `OUTERWEAR` — Верхняя одежда, `FOOTWEAR` — Обувь, `ACCESSORIES` — Аксессуары. Виды осадков: `NONE` — Нет, `RAIN` — Дождь, `SNOW` — Снег, `SLEET` — Дождь со снегом. Коды хранятся строками в таблицах, а не перечислениями в коде приложения.

Чтение справочников доступно всем трём активным ролям по JWT: `GET /api/reference/garment-categories` и `GET /api/reference/precipitation-types`. Ответ содержит только `id`, `code`, `name` в порядке ID. Пагинация — `page` с 0 и `size` от 1 до 50, по умолчанию 0/50; без общего числа записей. Некорректные параметры и смещение, превышающее целочисленный диапазон JPA, отклоняются с 400. Без входа и при блокировке — 401.

### Текущие значения и история

Для `app_user`, `garment` и `outfit_rating` используются `version`, `created_at`, `modified_at` и отдельные таблицы `_history`. В `outfit_rating` хранится одна текущая запись на `(outfit_id, stylist_id)`; полная последовательность оценок складывается из неё и `outfit_rating_history`.

Новая запись получает версию 1 и одинаковые даты создания и изменения. При обновлении прежнее состояние переносится в историю, версия увеличивается, а `modified_at` обновляется. Проверка ожидаемой версии, запись истории и обновление выполняются атомарно. Конфликт версии или ошибка откатывают всю операцию.

Ключ истории пользователя или вещи — ID основной записи и версия; у оценки — `(outfit_id, stylist_id, version)`. Порядок состояний определяется версией, а не временем. Даты задаются сервером и хранятся как `timestamptz`: исторический `modified_at` относится к сохранённому состоянию, `archived_at` — к моменту его переноса в историю.

История не редактируется и не очищается при DELETE. `garment_history.garment_id` и `outfit_rating_history.outfit_id` остаются частью исторического ключа, но не являются FK на удаляемые записи. Составного FK из истории оценок на текущую оценку нет; `stylist_id` ссылается непосредственно на `app_user`. Связи истории с пользователями и справочниками сохраняются, поскольку их удаление не предусмотрено. ID удалённых сущностей не переиспользуются.

История хранит версии изменяемых бизнес-полей, а не полный архив объекта. Исходный `created_at` и неизменяемый владелец вещи не дублируются в каждой версии; после удаления основной записи эти сведения недоступны. История оценок сохраняет ID образа и стилиста, но не состав или владельца удалённого образа. Хеши паролей в историю не копируются. Роль и статус аккаунта в текущей записи и истории используют общие PostgreSQL enum-типы `user_role` и `user_status`. API восстановления по истории нет.

Перед удалением вещи её последнее состояние сохраняется в `garment_history`. Перед удалением образа последнее состояние каждой текущей оценки сохраняется в `outfit_rating_history`. Снимок получает существующий номер версии: новая текущая версия не создаётся. Это относится и к записям версии 1, которые ни разу не изменялись.

Сохранение снимков и DELETE выполняются одной транзакцией с защитой от конкурентных изменений. Если удаление запрещено или завершилось ошибкой, снимки также откатываются. Успешное изменение вещи или оценки не должно теряться между чтением последней версии и удалением.

### Неизменяемые данные

Содержимое `outfit` и `garment_photo` неизменяемо: у них есть `created_at`, но нет `modified_at`, `version` и `_history`. Состав и погода не имеют отдельного жизненного цикла и удаляются вместе с образом; время создания погоды берётся из него. Сохранение истории оценок не означает сохранения самого удалённого образа.

### Ограничения и транзакции

Предлагаемые ограничения БД:

- обязательные ключи, номера версий и даты;
- уникальные логин, ключ S3 в пределах бакета и позиция вещи внутри образа;
- обязательные ссылки на категорию и вид осадков, уникальные непустые коды справочников.

ID пользователя генерируется через `BIGSERIAL`. Непустые логин и хеш пароля проверяются в Entity через `@NotBlank`; SQL-проверки непустых строк и `version >= 1` для пользователя и его истории не используются. Начальную версию 1 и её увеличение при изменении обеспечивает приложение.

Принадлежность вещей владельцу образа, права стилиста и запрет самооценки проверяются отдельно: одних FK для этого недостаточно.

В проекте БД запрет удаления используемой вещи задаётся через `outfit_item.garment_id → garment.id ON DELETE RESTRICT`. Для фотографий вещи, состава, погоды и текущих оценок образа используется `ON DELETE CASCADE`. История не входит в эти каскады. Действия внешних ключей описаны в [документации PostgreSQL](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-FK).

Транзакции охватывают создание вещи с метаданными фото, создание образа с составом и погодой, изменение записи с сохранением истории, а также сохранение последних версий и удаление вещи или образа с зависимыми записями. Ошибка откатывает все изменения БД; файлы S3 при DELETE не затрагиваются.

## Технические требования ЛР1

Основание — [задание лабораторной работы](https://github.com/Discipliny/highload_systems).

| Область | Требования |
|---|---|
| API | REST, корректные HTTP-статусы и ошибки. CRUD вещей с физическим удалением; для неизменяемых образов — создание, чтение и физическое удаление. Удаление используемой вещи отклоняется. |
| Данные | Spring Data JPA; миграции Flyway; перечисления сопоставляются по именам, не по числовым позициям. |
| Валидация | Проверки в контроллерах и Entity, раздельные Entity и DTO. |
| Пагинация | Все выдачи коллекций ограничены 50 элементами. Нужны варианты без total и с total в HTTP-заголовке. Предлагается применить их к гардеробу и образам соответственно. |
| Запуск | Сборка Docker-образа, запуск приложения и PostgreSQL через Docker Compose, конфигурация через переменные окружения. |
| Тесты | JUnit Jupiter и Testcontainers, общее покрытие не менее 70%. Внешние интеграции проверяются без платных вызовов. |
| Документация | OpenAPI 3 и общий Swagger. |

Каждый этап выполняется в feature-ветке и вливается в `main`; сообщения коммитов — Conventional Commits. Перед фиксацией результаты этапа проходят пользовательское ревью.
