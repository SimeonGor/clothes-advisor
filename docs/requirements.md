# Сервис подбора одежды — требования к ЛР1

## О проекте

Сервис помогает составлять образы из личного гардероба с учётом погоды. Пользователь загружает фотографии вещей, описывает их и выбирает погодные условия. Образ можно собрать самостоятельно, поручить стилисту или получить через OpenAI.

Приложение — монолит на Kotlin и Spring Boot. Данные хранятся в PostgreSQL и обрабатываются через Spring Data JDBC. Фотографии — в приватном Yandex Object Storage; сервис обращается к HTTP API с IAM-токеном, без AWS SDK.

В ЛР1 используются заранее созданные тестовые аккаунты. Регистрации, создания аккаунтов через API и интеграции с погодным сервисом нет. Реализация ведётся небольшими отдельными этапами.

В ЛР1 удаление выполняется физически — через `DELETE` строки из таблицы. История изменений и файлы S3 сохраняются, остальные зависимые записи удаляются. Вещь нельзя удалить, пока она входит хотя бы в один образ. Архивирование и восстановление отложены; правила будущего архива описаны отдельно.

## Пользователи и доступ

| Роль | Возможности |
|---|---|
| USER | Ведёт свой гардероб, создаёт и удаляет свои образы, запускает AI-подбор, выдаёт и отзывает доступ стилистам. |
| STYLIST | С разрешения владельца просматривает его гардероб и образы, создаёт образы и оценивает чужие работы. |
| ADMIN | Назначает роли, блокирует и разблокирует аккаунты. Просматривает и удаляет фотографии и образы для модерации без разрешения владельца. Не выставляет оценки. |

Разрешение выдаётся конкретному стилисту сразу на весь гардероб и все образы владельца. При отзыве стилист теряет доступ, в том числе к фотографиям, и больше не может создавать образы или менять оценки этого клиента. Прежние оценки и их история сохраняются и продолжают учитываться в счётчиках. Повторная выдача доступа не создаёт дополнительного голоса.

Разрешение действует только между владельцем ACTIVE USER и стилистом ACTIVE STYLIST. Блокировка или смена роли любого участника не удаляет пару, но приостанавливает доступ. После восстановления подходящих роли и статуса доступ возобновляется автоматически. Сам отзыв удаляет пару и требует повторной выдачи владельцем.

У аккаунта два статуса: `ACTIVE` и `BLOCKED`. В сценариях с действующим пользователем требуется активный аккаунт. Блокировка не удаляет данные. Менять статус может только администратор; изменение сохраняется в истории пользователя.

Администратор не может заблокировать себя или снять собственную роль ADMIN. В системе должен оставаться хотя бы один активный администратор; это правило действует и при одновременных запросах нескольких администраторов.

Секреты и изображения не попадают в логи или Git. Хеши паролей, оставшиеся в БД от прежней версии, не используются для входа и не возвращаются в ответах. Бакет остаётся приватным; сервис не выдаёт прямые URL фотографий.

### Выбор действующего пользователя

В локальной ЛР1 нет входа, Spring Security, JWT и контроля ролей на маршрутах API. Для сценариев, которым нужен действующий пользователь, клиент передаёт его ID в заголовке `X-User-Id`. Демонстрационный интерфейс позволяет выбрать тестового пользователя. Заголовок не подтверждает личность: любой клиент может подставить чужой ID, поэтому публикация этой версии в открытый интернет запрещена.

Проверяются формат ID и существование активного аккаунта: отсутствующий или некорректный заголовок даёт 400, неизвестный аккаунт — 404, заблокированный — 403. Чтение справочников и списка аккаунтов не требует заголовка. Бизнес-правила сохраняются в сервисах: принадлежность данных, действительность разрешения стилисту, запрет самооценки и правила административных изменений. Они не заменяют аутентификацию.

Профиль `local` создаёт отсутствующие аккаунты `user`, `stylist` и `admin` с соответствующими ролями, без паролей для входа. Повторный запуск не меняет существующие аккаунты. Без локального профиля аккаунты автоматически не создаются. Логин — непустая строка длиной до 100 символов.

### Управление аккаунтами

`GET /api/admin/users` открыто возвращает список аккаунтов, включая заблокированные, по убыванию ID: page начинается с 0, size — от 1 до 50, значения по умолчанию 0/50. Общее число аккаунтов передаётся в `X-Total-Count`. `GET /api/admin/users/{id}` возвращает карточку с id, login, role, status, version, createdAt и modifiedAt. Пароль и хеш в ответы не входят.

`PUT /api/admin/users/{id}` принимает role, status и текущую version. Успешное изменение возвращает 200 с карточкой, увеличивает версию и сохраняет прежнее состояние в истории в одной транзакции. Запрос с теми же значениями и актуальной версией ничего не меняет. Устаревшая версия, попытка заблокировать себя или снять собственную роль ADMIN возвращают 409. Неизвестный аккаунт — 404; неверные поля или параметры пагинации — 400. Роли и статусы задаются строками, числовые значения не принимаются.

Перед изменением сервис проверяет действующего администратора под блокировкой строк участников. Если он не ADMIN или был заблокирован, запрос завершается с 403 без изменения данных. Роль берётся из БД, а не из заголовка клиента.

Создания и удаления аккаунтов, изменения логина/пароля, поиска и отдельного API истории на этом этапе нет. Модерация фотографий и образов реализуется отдельно.

## Административная модерация

Активный ADMIN может просматривать контент любого существующего аккаунта без разрешения владельца, в том числе после блокировки владельца или смены его роли. Навигация идёт от выбранного аккаунта к его вещам, фотографиям и образам; общей ленты нет.

`GET /api/admin/users/{ownerId}/wardrobe/items` возвращает вещи владельца, а `GET /{itemId}` относительно этого пути — карточку. Пагинация и DTO совпадают с личным гардеробом: page/size 0/50, размер 1–50, ID по возрастанию, без total. Вложенные маршруты `GET /{itemId}/photos` и `GET /{itemId}/photos/{photoId}/content` возвращают метаданные и файл. Файл выдаётся без прямого URL S3, с no-store и nosniff. `DELETE /{itemId}/photos/{photoId}` удаляет метаданные и возвращает 204; файл в S3 сохраняется.

`GET /api/admin/users/{ownerId}/outfits` и `GET /api/admin/users/{ownerId}/outfits/{id}` возвращают образы с составом, погодой и счётчиками оценок, без myRating. Список использует page/size 0/50, размер 1–50, ID по убыванию и X-Total-Count. `DELETE /api/admin/users/{ownerId}/outfits/{id}` возвращает 204; удаление и сохранение финальных версий оценок в истории выполняются атомарно. Вещи гардероба не удаляются.

Несуществующий владелец, неверная связь владельца/вещи/фото/образа и повторное удаление дают 404; неверная пагинация — 400, недоступность S3 — 503. ADMIN не получает права создавать или редактировать контент, удалять вещи, оценивать образы или читать историю оценок через административный API. Причина удаления и отдельный журнал модерации пока не вводятся.

Перед удалением сервис повторно проверяет актуальные права администратора после получения блокировки вещи или образа. При скачивании файла права и наличие фотографии проверяются до и после обращения к S3, без открытой транзакции БД во время внешнего вызова. Если ADMIN заблокирован или сменил роль, запрос возвращает 403 без удаления или выдачи файла.

## Гардероб и фотографии

На одной фотографии находится одна вещь. Пользователь указывает название, выбирает категорию из справочника и вручную вводит цвет и материал. Эти четыре поля обязательны; название, цвет и материал — непустые строки. Название вещи ограничено 300 символами, цвет и материал — 100 при создании и изменении; значения не обрезаются автоматически. Ограничения действуют и в API, и в БД. Цвет и материал хранятся отдельными текстовыми колонками, без дополнительного справочника и общего поля characteristics.

Карточку своей вещи можно создать, просмотреть, изменить и удалить. Владелец определяется по `X-User-Id`, а не по полям JSON. Ограничения роли на личных маршрутах нет. Стилист читает данные другого владельца через отдельные маршруты ниже, ADMIN использует маршруты модерации. Чужая и отсутствующая вещь дают одинаковый 404.

`POST /api/wardrobe/items` создаёт вещь и возвращает 201 с карточкой и Location; `GET /api/wardrobe/items/{id}` возвращает свою вещь. `GET /api/wardrobe/items` выдаёт только свои вещи по возрастанию ID: page начинается с 0, size — от 1 до 50, значения по умолчанию 0/50, без total. Неверные параметры или смещение за пределами поддерживаемого диапазона — 400.

`PUT /api/wardrobe/items/{id}` принимает все четыре поля и ожидаемую version. Успешное изменение возвращает 200, увеличивает версию и сохраняет прежнее состояние в истории. Повторная отправка неизменившихся значений не создаёт новую историю, но проверка версии остаётся обязательной. `DELETE /api/wardrobe/items/{id}?version=…` физически удаляет вещь и возвращает 204; последняя версия сохраняется в истории, в том числе если вещь не изменялась после создания.

Ответ карточки содержит id, name, categoryId, color, material, version, createdAt и modifiedAt. Некорректные данные и неизвестная категория — 400, конфликт версии — 409. История пока доступна только в БД: отдельного API её просмотра нет.

Фотографии хранятся в приватном S3, ключи объектов и метаданные — в БД. HTTP-клиент использует IAM-токен, который приложение получает по авторизованному ключу сервисного аккаунта и автоматически обновляет перед истечением срока. Путь к JSON-файлу ключа задаётся через `YANDEX_SERVICE_ACCOUNT_KEY_FILE`; файл хранится вне репозитория и монтируется в контейнер только для чтения. При сбое IAM допускается использовать прежний токен, пока он действителен; без действующего токена обращение к S3 не выполняется и операция возвращает 503. AWS SDK и статические S3-ключи не используются. Логи содержат операцию, длительность, результат, размер и безопасный ID запроса провайдера, без токена, ключа, содержимого фото и внутренних ответов. Вещи без доступных фотографий не участвуют в AI-подборе до загрузки фото.

У вещи может быть до пяти фотографий JPEG или PNG, каждая не более 10 000 000 байт. Фото можно добавить при создании карточки или отдельно позже. Формат определяется по содержимому заголовка файла, а не расширению или MIME клиента; полное декодирование и распознавание изображения не выполняются. Тип и размер сохраняются в отдельных полях метаданных. Само фото неизменяемо: для замены нужно удалить старое и загрузить новое. Эти операции не меняют версию и историю текстовых полей вещи.

`POST /api/wardrobe/items` дополнительно принимает multipart с JSON-частью `item` и необязательными файлами `photos`. Карточка и все метаданные сохраняются одной транзакцией; ответ такой же, как при JSON-создании без фото. Добавить от одного до пяти файлов к существующей вещи можно через multipart `POST /api/wardrobe/items/{itemId}/photos`; ответ 201 содержит список созданных фотографий. `GET` того же маршрута возвращает все фото вещи по ID — не более пяти записей с полями id, itemId, contentType, sizeBytes, createdAt.

`GET /api/wardrobe/items/{itemId}/photos/{photoId}/content` возвращает файл через сервис после проверки прав, без прямого URL S3 и с запретом кеширования. Наличие метаданных проверяется повторно после чтения S3: удалённое во время загрузки фото не выдаётся. Уже отправленный клиенту файл отозвать невозможно. `DELETE /api/wardrobe/items/{itemId}/photos/{photoId}` удаляет строку фотографии и возвращает 204. Несуществующее фото, фото чужой вещи или несовпадение itemId и photoId дают 404.

Пустой файл или некорректный заголовок изображения — 400, неподдерживаемый формат — 415, слишком большой файл — 413, больше пяти файлов в запросе — 400. Если итоговое количество фото превышает пять, запрос отклоняется с 409; это правило действует и при одновременных загрузках. При недоступности S3 сервис возвращает 503 без внутренних подробностей. Ошибки загрузки не оставляют частично сохранённые карточки или метаданные в БД. Уже загруженные объекты при последующем сбое могут остаться в приватном S3, но сервис их не выдаёт; автоматической очистки нет.

## Разрешения и просмотр стилистом

Владелец указывает известный ID стилиста. `PUT /api/me/stylist-access/{stylistId}` выдаёт разрешение, `DELETE` того же маршрута отзывает его. Владелец берётся из `X-User-Id`. Успешные запросы возвращают 204, включая повторные. PUT, в том числе повторный, требует активного адресата с ролью STYLIST; неизвестный, заблокированный или неподходящий адресат — 404. Отзыв допустим независимо от текущего состояния адресата, отсутствие пары не является ошибкой. Конкурентные выдачи не создают дубликаты.

`GET /api/me/stylist-access` возвращает всех адресатов сохранённых разрешений владельца, включая временно не действующие. `GET /api/stylist/clients` возвращает только доступных сейчас владельцев. В обоих случаях элементы содержат id и login; порядок — по ID, пагинация page/size с 0/50 по умолчанию и размером 1–50, без total. Неверные параметры и смещение за пределами поддерживаемого диапазона — 400.

Чтение клиентского гардероба доступно только STYLIST:

- `GET /api/stylist/clients/{ownerId}/wardrobe/items` — вещи с прежней пагинацией и DTO;
- `GET /api/stylist/clients/{ownerId}/wardrobe/items/{itemId}` — карточка;
- `GET /api/stylist/clients/{ownerId}/wardrobe/items/{itemId}/photos` — список фото;
- `GET /api/stylist/clients/{ownerId}/wardrobe/items/{itemId}/photos/{photoId}/content` — файл с прежними приватными заголовками.

На каждом чтении проверяются пара разрешения и актуальные роли/статусы обоих участников. Отсутствие доступа, неподходящий владелец, отсутствующая вещь/фотография или несоответствие ownerId/itemId/photoId дают одинаковый пустой 404. Действующий пользователь определяется по `X-User-Id`; отдельной проверки роли на маршруте нет. STYLIST не получает права создавать, изменять или удалять вещи и фото клиента.

После внешнего чтения S3 сервис повторно проверяет метаданные, разрешение и состояние обоих участников. Если на этой проверке разрешение отозвано или роли/статусы больше не подходят, файл не выдаётся. Возвращённые клиенту байты отозвать нельзя; кратковременный отзыв с повторной выдачей до последней проверки не фиксируется отдельной историей событий. Транзакция БД не удерживается во время S3-запроса.

## Образы, погода и оценки

Пользователь задаёт десятичные температуру в °C и скорость ветра в м/с, а вид осадков выбирает из справочника. Скорость ветра неотрицательна; дополнительных ограничений температуры и точности нет. Эти условия сохраняются вместе с образом и не обновляются вслед за текущей погодой.

Название образа обязательно, не может состоять только из пробелов и содержит не более 300 символов. Ручной образ включает от 1 до 50 разных вещей владельца, в порядке, заданном при создании. Фотографии для ручного образа не обязательны.

USER создаёт и просматривает свои образы через `POST/GET /api/outfits`, читает и удаляет отдельный образ через `GET/DELETE /api/outfits/{id}`. STYLIST с действующим разрешением создаёт и читает образы клиента через `POST/GET /api/stylist/clients/{ownerId}/outfits` и `GET /api/stylist/clients/{ownerId}/outfits/{id}`. Удалять образы стилист не может. Владелец и автор определяются сервером; источник фиксируется как USER или STYLIST, а не принимается из запроса.

Запрос создания содержит name, itemIds и weather с полями temperatureC, precipitationTypeId, windSpeedMps. Ответ 201 содержит id, ownerId, authorId, source, name, itemIds, weather, createdAt и заголовок Location. Список возвращает массив таких же карточек по убыванию ID: page начинается с 0, size — от 1 до 50, по умолчанию 0/50. Общее количество доступных образов владельца передаётся в X-Total-Count, в том числе для пустой страницы.

Некорректный запрос, повторные ID вещей и неизвестный вид осадков — 400. Недоступный клиент, чужая или отсутствующая вещь либо образ — одинаковый пустой 404. Конфликт сохранения или попытка удалить вещь из образа — 409. Удаление образа возвращает 204. Образ, состав и погода создаются одной транзакцией; удаление образа удаляет его состав и погоду, но не вещи.

Стилист составляет образ из вещей клиента: клиент остаётся владельцем, а стилист — автором. Сохранённые образ, состав и погода не редактируются. Изменение состава создаёт новый образ с отдельным ID и без переноса оценок. При этом ссылки на вещи не фиксируют их прежний внешний вид: изменения характеристик и доступности фотографий видны и в старых образах.

Для AI-подбора используются существующие вещи владельца с доступными фотографиями. Сервис передаёт фотографии и описание задачи в [OpenAI](https://developers.openai.com/api/docs/guides/images-vision), перед сохранением результата повторно проверяет наличие вещей, их владельца и доступность фото. Ошибка интеграции не должна приводить к сохранению образа как успешно подобранного. Результат доступен пользователю сразу, без предварительного одобрения стилистом.

`POST /api/outfits/ai` доступен только USER. Обязательны name (до 300 символов) и weather прежнего формата; candidateItemIds — необязательный список кандидатов. Отсутствующее поле или null означает весь гардероб владельца, пустой массив недопустим. Вещи без фото исключаются; чужие и несуществующие ID в явном списке возвращают одинаковый 404, а не пропускаются. После исключения вещей без фото должно остаться от 1 до 20 кандидатов; для каждой вещи берётся фото с наименьшим ID. При превышении лимита требуется явный более узкий список, без молчаливого усечения гардероба.

Подбор синхронный: один запрос сохраняет один неизменяемый образ с source=AI, ownerId и authorId текущего пользователя. Ответ 201 содержит прежний OutfitResponse и Location; дальнейшее чтение, оценки и удаление используют существующие маршруты. Дополнительных текстовых пожеланий, запуска от STYLIST/ADMIN и фоновых задач нет.

Неверные поля, повторные ID, отсутствие подходящих вещей или превышение лимита — 400 до обращения к S3/OpenAI. Если использованную вещь или фотографию удалили во время подбора, ответ — 409; если инициатор потерял права — 403. Отказ модели или невозможность составить образ — 422; некорректный/неполный ответ, повторные ID результата либо выбор вне кандидатов — 502. Недоступность S3/OpenAI — 503, таймаут OpenAI — 504. Любая ошибка не оставляет образа или частично сохранённого состава/погоды.

Для локальной ЛР1 используется личная подписка через Sign in with ChatGPT, привязанная к тестовому аккаунту `user`. Остальные USER получают 503 при AI-подборе; роль и активность инициатора остаются бизнес-проверкой AI-сервиса. Вход в ChatGPT выполняется отдельной утилитой и не связан с выбором пользователя приложения. Сервис только читает credentials из каталога CHATGPT_CREDENTIALS_DIR вне Git и БД. После истечения токена нужен повторный вход; автоматического обновления и API управления подключением пока нет. Модель задаётся через OPENAI_MODEL. API-ключ, автоматический платный fallback и дополнительные кредиты не используются; отключение кредитов пользователь подтверждает в настройках ChatGPT Usage.

Без действующего подключения AI-подбор возвращает503, остальные функции работают. Responses API вызывается с store=false и stream=true; таймаут60секунд включает чтение потока, автоматических повторов нет. Только response.completed с корректным результатом позволяет сохранить образ. Сервис проверяет структурированный список ID и не раскрывает клиенту токены, внутренние ответы провайдера или адреса S3. Фотографии передаются непосредственно в запросе, бакет остаётся приватным. Согласованный корпоративный CA при необходимости подключается через отдельный SSLContext только клиенту OpenAI, без изменения глобального TLS-доверия и клиента S3.

Оценивать образ может только стилист с действующим доступом к гардеробу владельца. Автор не оценивает собственную работу. У каждого стилиста один текущий голос на образ — `LIKE` или `DISLIKE`. Новая оценка заменяет текущую и сохраняет предыдущее состояние, даже если значение голоса не изменилось. Счётчики учитывают только текущие голоса.

`POST /api/stylist/clients/{ownerId}/outfits/{id}/rating` принимает vote и создаёт текущую оценку: ответ 201 содержит vote и version. Первый голос получает версию 1; после отмены новая версия на единицу больше последней сохранённой для этой пары образ/стилист. Создание при уже существующей текущей оценке — 409; конфликт определяется результатом SQL-вставки, без предварительного чтения оценки. `PUT` того же маршрута принимает vote и ожидаемую version, возвращает 200 с новой текущей оценкой; устаревшая версия — 409, отсутствующая оценка — 404. Неверные данные дают 400, самооценка — 403. Стилист определяется по `X-User-Id`, а не по полям JSON.

`DELETE /api/stylist/clients/{ownerId}/outfits/{id}/rating?version=…` отменяет собственный голос. Права те же, что при изменении: активный стилист с действующим доступом, не автор образа. Обязательная version — положительное целое число. Ответ — 204 без тела; устаревшая версия — 409, отсутствие текущей оценки или недоступный образ — 404, неверный параметр — 400. Последнее состояние сохраняется в истории под прежней версией, текущая запись удаляется, счётчик уменьшается и myRating становится null. Отмена и сохранение истории атомарны. Уже отменённый голос повторно отменить нельзя; история при этом не меняется.

Карточка и список образов содержат likes и dislikes — число текущих голосов каждого вида. В ответах стилисту дополнительно возвращается myRating с vote и version либо null, если его оценки нет. Отзыв разрешения и изменение роли или статуса автора голоса не исключают уже сохранённую оценку из счётчиков.

Владелец читает историю через `GET /api/outfits/{id}/ratings/history`, стилист с действующим разрешением — через `GET /api/stylist/clients/{ownerId}/outfits/{id}/ratings/history`. Оба видят все оценки образа, включая текущие состояния и прошлые версии. Элемент содержит stylistId, vote, version, modifiedAt и archivedAt; у текущего состояния archivedAt равен null. Порядок — modifiedAt по убыванию, затем stylistId и version по убыванию для одинакового времени. Пагинация page/size — 0/50 по умолчанию, size от 1 до 50; общее число состояний передаётся в X-Total-Count.

После удаления образа история остаётся в БД, но оба API её просмотра возвращают 404. История не сохраняет владельца удалённого образа; дополнительного API для таких записей нет.

Создание, изменение и отмена оценки, а также удаление образа блокируют строку образа до конца короткой транзакции. После ожидания блокировки проверяются актуальное разрешение и состояние оценки. Это позволяет сохранить последнее состояние каждого голоса при DELETE без потери конкурентного изменения. Версия оценки увеличивается явно под этой блокировкой, в том числе при неизменных vote и временной метке; при повторном голосовании после отмены учитываются версии из истории. Чтение истории и счётчиков использует согласованный снимок данных; список образов не выполняет отдельный запрос оценок для каждой карточки.

## Удаление в ЛР1

Удаление вещи, фотографии или образа означает удаление основной строки из PostgreSQL, без перевода в архив. Отзыв доступа удаляет действующую пару из `access_grant`; прежние оценки стилиста и их история от этого не меняются.

| Что удаляется | Правило |
|---|---|
| Вещь, входящая хотя бы в один образ | Удаление запрещено. Вещь, состав образа, фото и история не меняются. |
| Вещь, не используемая в образах | Удаляются вещь и строки её фотографий. История вещи сохраняется. |
| Фотография | Удаляется строка с ключом S3 и метаданными. Вещь и состав образов остаются. |
| Образ | Удаляются образ, его состав, погода и текущие оценки. История оценок и сами вещи сохраняются. |
| Собственный голос стилиста | Последняя версия переносится в историю, текущая оценка удаляется. Требуются доступ и актуальная версия. |

Файлы фотографий остаются в приватном S3 и при отдельном удалении фото, и при удалении вещи. Без действующей строки `wardrobe_item_photo` сервис не выдаёт файл и не использует его для AI-подбора. Сохранение файла не означает сохранения метаданных или возможности восстановления через API. Автоматической очистки файлов и истории нет.

Удаление основной строки и её зависимостей выполняется одной транзакцией. Проверка запрета удаления используемой вещи должна работать и при одновременном создании образа; отдельной предварительной проверки в приложении недостаточно. Удаление аккаунтов и справочников не входит в ЛР1.

## Архивирование — дальнейшее развитие

Архивирование пока не реализуется. Для его последующего добавления приняты следующие правила.

При архивировании вещи её статус меняется с `ACTIVE` на `ARCHIVED`. Она исчезает из активного гардероба и больше не используется в новых ручных и AI-образах. В уже сохранённых образах вещь остаётся вместе с фотографиями и историей.

Архивирование фотографии — отдельная операция. Сам файл сохраняется в приватном S3, ключ и метаданные — в БД. Сервис не выдаёт архивное фото ни в карточке вещи, ни в старых образах и не передаёт его в AI-подбор. Сама вещь остаётся в гардеробе; если доступных фотографий больше нет, AI-подбор её не использует до загрузки нового фото.

Архивный образ сохраняет состав, погоду, оценки и историю, но недоступен для обычного просмотра, в том числе по прямому ID, и для новых оценок. Администратор сохраняет модерационный доступ. Архивирование образа не затрагивает вещи гардероба.

Архивирование не удаляет связанные записи каскадом. Автоматическая очистка историй, будущих архивов и архивных файлов S3 не предусмотрена. Отдельные операции удаления аккаунтов и справочников не вводятся. Восстановления в ЛР1 не будет; его дальнейшие правила пока не определены.

## Архитектура

[Схема монолита](architecture.png) · [исходник PlantUML](architecture.puml)

Приложение работает одним процессом и использует общую PostgreSQL. Внутри выделены пять модулей:

| Модуль | Ответственность |
|---|---|
| Пользователи | Выбор действующего пользователя, роли, статусы и история аккаунтов. |
| Гардероб и фотографии | Вещи, категории, характеристики и хранение фото. |
| Образы | Авторство, владелец, состав и погодные условия. |
| Доступ и оценки | Разрешения стилистам, текущие голоса, история и счётчики. |
| AI-подбор | Обращение к OpenAI, проверка и сохранение результата. |

Модули взаимодействуют через вызовы методов. Контроллеры и DTO отделены от сервисов, моделей и репозиториев. Административные операции выполняются в тех же модулях с проверкой роли. Вызовы S3 и OpenAI проходят вне транзакций БД.

Пакеты организованы сначала по техническим слоям, затем по предметным областям: например, `model.user`, `repository.user`, `service.user`. Новые контроллеры и DTO следуют тому же правилу. Бизнес-модули на схеме описывают ответственность, а не верхний уровень пакетов.

## Организация данных

[ER-модель](domain.png) · [исходник PlantUML](domain.puml)

Схема выполнена в нотации Crow’s Foot. Таблицы и поля именуются в `snake_case`; первичные, внешние и уникальные ключи обозначены как PK, FK и UK. Это проект схемы БД, который ещё нужно согласовать с преподавателем. Ориентир — третья нормальная форма. Цвет и материал вещи, тип и размер файла представлены отдельными полями.

ER отражает ЛР1 с физическим удалением: архивных таблиц и статуса `ARCHIVED` вещи в ней нет. Версии и таблицы `_history` сохраняются; история вещи и оценок не зависит от существования удалённой основной строки.

В коде вещь представлена `WardrobeItem`, её история — `WardrobeItemHistory`, категория — `WardrobeCategory`, фотография — `WardrobeItemPhoto`. Им соответствуют таблицы `wardrobe_item`, `wardrobe_item_history`, `wardrobe_category` и `wardrobe_item_photo`. Старые имена garment заменяются отдельной миграцией с сохранением данных; ранее применённые миграции не изменяются.

### Связи и справочники

- Категории хранятся в `wardrobe_category`, виды осадков — в `precipitation_type`. Оба справочника содержат `id`, уникальный `code` и `name`. Вещь и её история ссылаются на категорию через `category_id`, не копируя название. ID и смысл используемых кодов должны оставаться стабильными. В ЛР1 начальное заполнение и изменения выполняются только миграциями; API редактирования и истории справочников нет.
- Погода хранится в `outfit_weather`: `outfit_id`, `temperature_c`, `precipitation_type_id`, `wind_speed_mps`. Ключ `outfit_id` одновременно является PK и FK. У каждого образа должна быть ровно одна погодная запись, создаваемая в той же транзакции. Сам PK/FK гарантирует лишь отсутствие второй записи.
- Состав хранится в `outfit_item` с ключом `(outfit_id, wardrobe_item_id)` и полем `position`. Это ManyToMany с дополнительным полем. Происхождение образа фиксируется в `outfit.source` при создании и не зависит от последующих изменений роли автора.
- `access_grant(owner_id, stylist_id)` — обычная ManyToMany без дополнительных полей: оба столбца составляют PK и ссылаются на пользователя. Отзыв удаляет пару и прекращает действие разрешения сразу, без переноса в `access_grant_archive`. Уже поставленные оценки и их история сохраняются.
- Связи пользователя с вещами, вещи с фотографиями и пользователя с его историей — OneToMany / ManyToOne.
- У `wardrobe_item_photo` есть `id`, `wardrobe_item_id` с FK на вещь, уникальный `s3_key`, `content_type`, `size_bytes` и `created_at`. Каждая фотография относится ровно к одной вещи; дополнительная таблица связей не нужна.

Начальные категории: `TOP` — Верх, `BOTTOM` — Низ, `ONE_PIECE` — Платья и комбинезоны, `OUTERWEAR` — Верхняя одежда, `FOOTWEAR` — Обувь, `ACCESSORIES` — Аксессуары. Виды осадков: `NONE` — Нет, `RAIN` — Дождь, `SNOW` — Снег, `SLEET` — Дождь со снегом. Коды хранятся строками в таблицах, а не перечислениями в коде приложения.

Чтение справочников открыто и не требует `X-User-Id`: `GET /api/wardrobe/categories` и `GET /api/weather/precipitation-types`. Ответ содержит только `id`, `code`, `name` в порядке ID. Пагинация — `page` с 0 и `size` от 1 до 50, по умолчанию 0/50; без общего числа записей. Некорректные параметры и смещение за пределами поддерживаемого диапазона отклоняются с 400.

### Текущие значения и история

Для `app_user`, `wardrobe_item` и `outfit_rating` используются `version`, `created_at`, `modified_at` и отдельные таблицы `_history`. В `outfit_rating` хранится одна текущая запись на `(outfit_id, stylist_id)`; полная последовательность оценок складывается из неё и `outfit_rating_history`.

Первая запись получает версию 1 и одинаковые даты создания и изменения. Для повторной оценки после отмены берётся следующая версия из истории этой пары образ/стилист, а даты создания и изменения задаются заново. При обновлении прежнее состояние переносится в историю, версия увеличивается, а `modified_at` обновляется. Проверка ожидаемой версии, запись истории и обновление выполняются атомарно. Конфликт версии или ошибка откатывают всю операцию.

Ключ истории пользователя или вещи — ID основной записи и версия; у оценки — `(outfit_id, stylist_id, version)`. Порядок изменений и конфликты определяются версией, а не временем. Технические даты формирует PostgreSQL и хранит как `timestamptz`. При создании `created_at` и `modified_at` получают `DEFAULT CURRENT_TIMESTAMP`; приложение не передаёт своё время. При изменении SQL явно устанавливает `modified_at = CURRENT_TIMESTAMP`, не меняя `created_at`. При no-op даты и версия остаются прежними.

История копирует точный предыдущий снимок, включая его `modified_at`; только `archived_at` получает время БД. `CURRENT_TIMESTAMP` означает начало транзакции, а не commit, и одинаков внутри неё. Последующая версия не обязана иметь строго большую дату. Триггеры не используются; API возвращает фактически сохранённые значения через `RETURNING` или чтение записи. `Clock` остаётся только там, где время участвует в логике приложения, например при проверке срока credentials ChatGPT.

История не редактируется и не очищается при DELETE. `wardrobe_item_history.wardrobe_item_id` и `outfit_rating_history.outfit_id` остаются частью исторического ключа, но не являются FK на удаляемые записи. Составного FK из истории оценок на текущую оценку нет; `stylist_id` ссылается непосредственно на `app_user`. Связи истории с пользователями и справочниками сохраняются, поскольку их удаление не предусмотрено. Суррогатные ID удалённых сущностей не переиспользуются. Составной ключ текущей оценки может появиться снова при повторном голосовании, но уже с новой версией.

История хранит версии изменяемых бизнес-полей, а не полный архив объекта. Исходный `created_at` и неизменяемый владелец вещи не дублируются в каждой версии; после удаления основной записи эти сведения недоступны. История оценок сохраняет ID образа и стилиста, но не состав или владельца удалённого образа. Хеши паролей в историю не копируются. Роль и статус аккаунта в текущей записи и истории используют общие PostgreSQL enum-типы `user_role` и `user_status`. API восстановления по истории нет.

Перед удалением вещи её последнее состояние сохраняется в `wardrobe_item_history`. При отмене голоса его последнее состояние сохраняется в `outfit_rating_history`; перед удалением образа так сохраняется каждая текущая оценка. Снимок получает существующий номер версии: новая текущая версия не создаётся. Это относится и к записям версии 1, которые ни разу не изменялись.

Сохранение снимков и DELETE выполняются одной транзакцией с защитой от конкурентных изменений. Снимок вещи формируется до удаления; внутри транзакции проверяемый по версии DELETE выполняется раньше INSERT истории. Это сохраняет одинаковый порядок захвата блокировок при изменении и удалении: сначала вещь, затем история. Если удаление или сохранение истории завершилось ошибкой, откатываются обе операции. Успешное изменение вещи или оценки не должно теряться между чтением последней версии и удалением.

### Неизменяемые данные

Содержимое `outfit` и `wardrobe_item_photo` неизменяемо: у них есть `created_at`, но нет `modified_at`, `version` и `_history`. Состав и погода не имеют отдельного жизненного цикла и удаляются вместе с образом; время создания погоды берётся из него. Сохранение истории оценок не означает сохранения самого удалённого образа.

### Ограничения и транзакции

Ограничения БД:

- обязательные ключи, номера версий и даты;
- уникальные логин, ключ S3 в пределах бакета и позиция вещи внутри образа;
- обязательные ссылки на категорию и вид осадков, уникальные непустые коды справочников.

ID пользователя генерируется через `BIGSERIAL`. В БД проверяются непустые текстовые поля, длина логина, цвета и материала до 100 символов, названий вещей и образов до 300, положительные версии и размеры фотографий, неотрицательная скорость ветра. Согласованные текстовые ограничения действуют и для снимков в истории. Новые ограничения добавляются отдельной миграцией: старые данные не обрезаются и не удаляются автоматически. Начальную версию 1 и её увеличение обеспечивает приложение; обновления и удаления проверяют ожидаемую версию в SQL.

Принадлежность вещей владельцу образа, права стилиста и запрет самооценки проверяются отдельно: одних FK для этого недостаточно.

В проекте БД запрет удаления используемой вещи задаётся через `outfit_item.wardrobe_item_id → wardrobe_item.id ON DELETE RESTRICT`. Для фотографий вещи, состава, погоды и текущих оценок образа используется `ON DELETE CASCADE`. История не входит в эти каскады. Действия внешних ключей описаны в [документации PostgreSQL](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-FK).

Транзакции охватывают создание вещи с метаданными фото, создание образа с составом и погодой, изменение записи с сохранением истории, отмену голоса, а также сохранение последних версий и удаление вещи или образа с зависимыми записями. Ошибка откатывает все изменения БД; файлы S3 при DELETE не затрагиваются.

## Технические требования ЛР1

Основание — [задание лабораторной работы](https://github.com/Discipliny/highload_systems).

| Область | Требования |
|---|---|
| API | REST, корректные HTTP-статусы и ошибки. CRUD вещей с физическим удалением; для неизменяемых образов — создание, чтение и физическое удаление. Удаление используемой вещи отклоняется. |
| Данные | Интерфейсы Spring Data JDBC, SQL в `@Query` и встроенный маппинг моделей. Простые чтения используют derived-методы; пакетная вставка состава образа — отдельный JDBC-фрагмент. Миграции выполняет Flyway; перечисления сопоставляются по именам, не по числовым позициям. JPA/Hibernate не используются. |
| Валидация | Проверки DTO и сервисных входов, ограничения БД; модели данных отделены от DTO. |
| Пагинация | Все выдачи коллекций ограничены 50 элементами. Нужны варианты без total и с total в HTTP-заголовке. Предлагается применить их к гардеробу и образам соответственно. |
| Запуск | Сборка Docker-образа, запуск приложения и PostgreSQL через Docker Compose, конфигурация через переменные окружения. |
| Тесты | Unit-тесты сервисов на JUnit Jupiter с Mockito, без Spring и БД. Интеграционные тесты PostgreSQL Testcontainers с подготовкой и проверкой данных через JDBC, общей конфигурацией и очисткой после каждого теста. Покрытие не менее 70%; внешние интеграции — на локальных заглушках. |
| Документация | README, требования и схемы PlantUML; в локальном профиле springdoc публикует Swagger UI и OpenAPI для `/api/**`. |

Каждый этап выполняется в feature-ветке и вливается в `main`; сообщения коммитов — Conventional Commits. Перед фиксацией результаты этапа проходят пользовательское ревью.
