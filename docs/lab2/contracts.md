# Контракты ЛР2

Действующие взаимодействия сервисов. Account обслуживает пользователей и разрешения; wardrobe проверяет их через Feign. Пользовательский AI-сценарий вызывает HTTP API recommendation через Feign и Eureka. [Архитектура и схемы](architecture.md).

## Внешний API и Gateway

Пути, методы, JSON, multipart, Location, X-Total-Count и тела прежних ошибок сохраняются. Gateway передаёт X-User-Id и не интерпретирует роль. Новые межсервисные отказы обрабатываются явно, без возврата ложного успеха.

POST вещей принимает JSON либо multipart с частями item/photos; добавление фото — multipart photos. DELETE вещи и отмена оценки требуют query-параметр version, как в текущем API. Создание пользователей по HTTP не добавляется.

Вещь имеет `availability`: `AVAILABLE` (доступна), `IN_LAUNDRY` (в стирке) или `STORED` (убрана). Новые вещи создаются доступными. Состояние меняется через существующий PUT карточки с текущей версией; пропуск или `null` сохраняет прежнее значение. Изменение только состояния тоже создаёт версию и предыдущий снимок истории. Карточки и списки возвращают текущее состояние; в старом сохранённом ответе Idempotency-Key поле может отсутствовать, исходный ответ не дополняется.

Недоступные вещи остаются в гардеробе и сохранённых образах; ручная сборка разрешена. Для AI они исключаются до загрузки фотографий и проверки общего лимита. Явные ID сначала проверяются на принадлежность владельцу, затем фильтруются. Если недоступна обязательная вещь при частичной замене, запрос возвращает 400: её нужно явно отметить для замены. Если любой подготовленный кандидат стал недоступен во время подбора, финальная проверка под блокировкой возвращает 409 без сохранения образа. Проверяется актуальное состояние, не вся версия вещи: изменение названия или цвета само по себе не отменяет подбор.

Редактор состояния и предупреждение при ручной сборке подключаются отдельным этапом интерфейса.

Gateway сначала сопоставляет точные account-пути, затем направляет остальные /api/** в wardrobe. Вложенные /api/admin/users/{ownerId}/… и /api/stylist/clients/{ownerId}/… не совпадают с account-шаблонами и обслуживаются wardrobe. POST /api/outfits/ai — отдельный маршрут, не операция над числовым ID.

Статика /, /index.html, /demo.js и /demo.css идёт во frontend. Общий /swagger-ui/index.html обслуживает Gateway; /v3/api-docs/account и /v3/api-docs/wardrobe проксируются к соответствующим сервисам. Спецификации раздельные, с относительным server URL `/`; запросы из UI используют текущий адрес Gateway. Неизвестные /api/** и все /internal/** через Gateway дают 404, не HTML страницы. Имена discovery не создают автоматических внешних маршрутов ко всем endpoint сервисов.

Пагинация списков: page/size, 0/50 по умолчанию, size ≤50. Списки вещей — ID по возрастанию без общего количества; образы — ID по убыванию с X-Total-Count. Остальные параметры/порядок/заголовки берутся из соответствующего текущего контроллера, без унификации поведения при переносе. Списки фото ограничены пятью записями на вещь.

## Предпочтения

Профиль содержит `preferredColorsAndMaterials` (любимые цвета и материалы), `avoidances` (чего избегать) и `additionalWishes` (дополнительные пожелания). Каждое поле необязательно, до 2000 символов. Отсутствие или `null` при сохранении превращается в пустую строку; прочий текст сохраняется без обрезания. Пустое значение означает отсутствие пожелания.

USER читает и сохраняет собственный профиль через `GET/PUT /api/me/style-preferences`. До первого сохранения GET возвращает 404, не создавая строку. PUT заменяет все три поля и возвращает 200 с сохранёнными значениями, `version`, `createdAt`, `modifiedAt`. Для первого сохранения `version` отсутствует или равна `null`; для обновления требуется текущая положительная версия. Неверная версия или конкурентное создание дают 409. Неизменённые данные с актуальной версией не создают новую версию или историю.

`GET /api/stylist/clients/{ownerId}/style-preferences` доступен стилисту только с действующим разрешением владельца. Смена ролей, блокировка или отзыв разрешения учитываются при каждом запросе. Недоступность account — 503; отсутствие доступа или профиля — 404. Изменять профиль клиента нельзя. Собственного профиля STYLIST/ADMIN и административного обхода прав нет.

При изменении прежний снимок сохраняется в `style_preferences_history` одной транзакцией с обновлением. Даты формирует PostgreSQL, история сохраняет исходные даты записи. Удаления, восстановления и отдельного API истории пока нет.

В интерфейсе USER открывает `/app/preferences`, стилист — вкладку предпочтений клиента. После конфликта версии или неизвестного результата записи форма сохраняет введённый текст и требует явной загрузки актуальных данных перед новым сохранением. Такая загрузка заменяет черновик; автоматической перезаписи нет.

## Идемпотентное создание

Необязательный заголовок `Idempotency-Key` поддерживают POST вещей (JSON и multipart), добавления фото, собственных образов, образов клиента стилиста и AI-образов. Без ключа сохраняется прежнее поведение. Ключ — от 1 до 255 печатных ASCII-символов; неверный формат даёт `400 invalid_idempotency_key`.

Ключ действует в пределах пользователя и типа операции. JSON и multipart создания вещи относятся к одной операции; ручное создание образов пользователем и стилистом — также к одной. Отпечаток запроса включает целевого владельца/вещь, поля запроса и упорядоченные байты файлов, но не multipart boundary. Другой запрос с тем же ключом получает `409 idempotency_key_reused`.

| Состояние команды | Повтор с тем же ключом и данными |
|---|---|
| RUNNING | `409 idempotency_in_progress`, без ожидания и повторного выполнения |
| SUCCEEDED | Исходные JSON, `201` и Location, если он предусмотрен маршрутом; без S3/AI |
| FAILED | `409 idempotency_failed`, без повторного выполнения |

Ошибки идемпотентности имеют тело `{"error":"..."}`. Права проверяются заново перед выдачей сохранённого ответа. Успешный ответ — снимок результата создания, не текущее состояние ресурса. Сохранение ресурса и ответа команды выполняется одной транзакцией; захват ключа фиксируется до внешних вызовов. Падение процесса может оставить RUNNING навсегда: автоматического восстановления, повторов и удаления ключей нет.

Версия серверного промпта не входит в отпечаток AI-запроса. Обновление промпта не меняет результат повтора SUCCEEDED и не запускает AI заново. Новый подбор с текущей инструкцией требует нового ключа.

Замена части образа — отдельный тип команды. Отпечаток включает ID исходного образа и тело запроса; успешный повтор возвращает сохранённый результат даже после удаления исходного образа, без повторного AI-вызова.

React-интерфейс хранит ключ и отпечаток в sessionStorage, без текста запроса и фотографий. После потери ответа повтор использует тот же ключ; после подтверждённого успеха или изменения данных — новый. Кнопка «Новая попытка» сбрасывает ключ только после предупреждения: неизвестный исход предыдущей операции может означать дубликат, лишнюю загрузку S3 или повторный расход AI-квоты. Это не гарантия exactly-once внешнего провайдера.

## Account: сведения и доступ

Вызовы доступны только внутри сети Compose через Feign. Внутренние ID передаются явно, а не извлекаются из пользовательского X-User-Id. Ответы не содержат password_hash, credentials или избыточные снимки истории.

| Метод и путь | Успех | Отказ |
|---|---|---|
| GET /internal/users/{userId} | 200: id, login, role, status | 404, если аккаунт отсутствует |
| GET /internal/stylist-access/{stylistId}/clients/{ownerId} | 204: есть grant, stylist = ACTIVE STYLIST, owner = ACTIVE USER | 404 при любом невыполненном условии |
| GET /internal/admin-access/{adminId}/users/{ownerId} | 204: admin = ACTIVE ADMIN, owner существует | Сначала 403 при неподходящем admin; затем 404 при отсутствии owner |

Пример сведений: `{"id":7,"login":"user","role":"USER","status":"ACTIVE"}`. GET пользователя возвращает и BLOCKED-аккаунт: проверка допустимого статуса зависит от сценария. Это не публичный endpoint и не способ входа.

ID имеют тип Long. Непарсируемый параметр — 400; отсутствующий числовой ID, включая неположительный, обрабатывается по таблице, а не получает новый публичный статус. Успех проверки доступа не возвращает токен/разрешение с TTL и не кэшируется. Account проверяет роли, статусы и grant по одному актуальному снимку своей БД.

Для внутренних ошибок account 400 имеет `{"code":"invalid_request"}`, 403 — `{"code":"forbidden"}`, 404 — пустое тело. Wardrobe сохраняет прежнее публичное представление ошибок. Сетевая недоступность, таймаут, открытый Circuit Breaker, 5xx или непригодный ответ account дают публичный 503 с пустым телом; операция не выполняется. Неожиданный внутренний 400 не выдаётся за ошибку данных пользователя.

Клиент account проверяет статус и структуру ответа, в том числе совпадение ID пользователя. Соединение ограничено 2 секундами, чтение — 5 секундами; дополнительный TimeLimiter отключён. Ожидаемые отказы 403/404 не учитываются как сбои Circuit Breaker. Feign и LoadBalancer не повторяют запросы; JDK-транспорт может повторить безопасный GET при обрыве соединения до ответа. Все проверки пользователей и разрешений в wardrobe обращаются к этому клиенту, без чтения старых account-таблиц wardrobe_db.

### Проверки в вызывающем сервисе

| Сценарий | Проверка и наблюдаемый результат |
|---|---|
| Начало запроса с CurrentUser | Нет/неверный/неположительный X-User-Id →400; аккаунт отсутствует →404; BLOCKED →403; ACTIVE любой роли допустим |
| Собственные вещи и обычные образы | Owner берётся из текущего пользователя, чужой ресурс →404. Ограничение только ролью USER не добавляется |
| Данные клиента стилиста | Проверка stylist-access; отсутствие доступа →404. После начальной проверки пользователя последующий отзыв/смена роли также даёт 404 |
| Модерация чужого контента | Проверка admin-access; роль и статус владельца не ограничены. BLOCKED-владельца можно модерировать |
| AI | ACTIVE USER и login разрешённого владельца подключения. При повторной проверке отсутствие/неактивность/иная роль →403; неподходящий login →503 |
| Оценка | Дополнительно в wardrobe: автор образа не может оценивать свой образ →403, актуальность version и история проверяются локально |

Проверки API аккаунтов и выдачи/отзыва grant остаются в account. Не вводится общий фильтр, который запрещал бы все /api/admin/** или собственные wardrobe/outfits только по имени роли. Source USER у самостоятельно созданного образа означает способ создания, а не ограничение роли автора.

### Момент проверки

Перед изменением данных wardrobe выполняет свежую проверку account, затем открывает локальную транзакцию и блокирует нужные строки. При подготовке через S3/AI проверка повторяется после внешних вызовов, непосредственно перед сохранением. Недавний CurrentUser из начала долгого запроса её не заменяет.

Если доступ отозван после успешной финальной проверки, разрешённая операция может завершиться, включая ожидание блокировки. HTTP-вызова после захвата блокировки внутри JDBC-транзакции нет. Следующая проверка видит отзыв. Для account-local операций сохраняются собственные транзакционные правила.

При скачивании проверяются и доступ, и наличие метаданных после S3, до выдачи байтов. Позднейший отзыв после этой проверки не даёт гарантии отмены уже начатой передачи. Гонки удаления вещей/фото в БД по-прежнему защищены локальными блокировками и повторными чтениями.

Это заменяет прежние ожидания тестов «отзыв во время ожидания блокировки отменяет оценку/модерацию» и AI-блокировку строки пользователя FOR SHARE. Остальные проверки прав, версий и истории сохраняются.

## Recommendation: выбор образа

В `POST /api/outfits/ai` можно указать `occasion` (повод) и `preferredStyle` (желаемый стиль): свободный текст, до 300 символов каждое. Поля необязательны; отсутствие и `null` означают отсутствие пожелания. Пустая строка допустима. API не обрезает текст; интерфейс убирает краевые пробелы и не отправляет пустые поля. Слишком длинный текст отклоняется с 400 до обращения к S3 и AI.

Пожелания сохраняются вместе с неизменяемым образом и возвращаются в его карточке и списке. У прежних и вручную созданных образов этих полей нет в JSON. Это исходный запрос пользователя, а не утверждение AI о стиле результата. Ручное создание не меняется.

Старые AI-запросы без пожеланий сохраняют прежний отпечаток `Idempotency-Key`. Переданный повод и стиль входят в отпечаток: изменение любого из них с уже использованным ключом даёт 409. Обновление серверного промпта по-прежнему не входит в отпечаток.

Обычный подбор и замена вещей читают текущий профиль владельца при подготовке запроса. Снимок трёх полей передаётся в recommendation как `stylePreferences`; отсутствие профиля не мешает подбору. Разовые `occasion`/`preferredStyle` важнее долгосрочных пожеланий. Изменение профиля во время S3/AI не меняет уже подготовленный запрос; новые пожелания учитываются при следующем подборе. Текущий профиль не входит в отпечаток `Idempotency-Key`: повтор завершённой операции возвращает прежний результат без нового AI. Отдельный снимок профиля в образе не хранится.

Для подключения предпочтений сначала обновляются recommendation и динамический промпт, затем wardrobe. Новый recommendation принимает старые запросы без профиля. Передаваемые пожелания остаются JSON-данными пользователя; высокоуровневые инструкции задаются отдельно в промпте Config Server.

Типы данных описаны в [серверном контракте](../../recommendation-service/src/main/kotlin/ru/itmo/clothesadvisor/dto/ai/OutfitSelectionDtos.kt) и независимом [контракте клиента](../../wardrobe-service/src/main/kotlin/ru/itmo/clothesadvisor/dto/recommendation/OutfitSelectionDtos.kt). Wardrobe вызывает recommendation через Feign; зависимости на код провайдера нет. Проверки владельца, исходных фотографий и сохранение остаются в wardrobe; перед сохранением он отдельно проверяет результат подбора.

`POST /api/outfit-selections`, Content-Type: application/json. Единственный API подбора recommendation, без отдельной публичной или `/internal`-копии. Wardrobe вызывает его напрямую через Feign и Eureka, без автоматических повторов. Маршрут не публикуется через Gateway: внешний запрос к `/api/outfit-selections` получает 404. Префикс `/api` не означает внешнюю доступность. Recommendation принимает данные, а не ссылку на гардероб или URL для самостоятельного скачивания.

| Поле | Содержание |
|---|---|
| weather.temperatureC | Десятичная температура, включая отрицательную |
| weather.windSpeedMps | Десятичная скорость ветра ≥0 |
| weather.precipitationCode, precipitationName | Код и название из справочника wardrobe |
| occasion, preferredStyle | Необязательные пожелания пользователя, до 300 символов каждое |
| stylePreferences | Необязательный снимок preferredColorsAndMaterials, avoidances, additionalWishes: три строки до 2000 символов, без ID и технических полей |
| requiredItemIds | При замене — различные положительные ID сохраняемых вещей из candidates; пустой список при полной замене |
| candidates | 1–20 кандидатов с различными положительными itemId |
| candidates[].itemId | ID вещи, допустимый в результате |
| candidates[].name, categoryCode, categoryName, color, material | Текущие характеристики вещи |
| candidates[].contentType | image/jpeg или image/png |
| candidates[].imageBase64 | Байты выбранного фото в стандартном Base64, без data-URL префикса |

Название будущего образа, ownerId, authorId, photoId и S3-ключи не нужны recommendation и туда не передаются. Wardrobe сохраняет исходные photoId локально для финальной проверки. Текст и изображения — данные, не инструкции модели.

Успех — 200, например `{"itemIds":[12,34],"explanation":"Рубашка и брюки подходят для работы в тёплую погоду."}`: непустой упорядоченный список уникальных ID из переданных кандидатов и краткое объяснение выбора. `explanation` — непустой обычный текст до 2000 символов; русский язык задаётся промптом. Неизвестные и повторные поля, неверный тип, `null`, пробельное или слишком длинное объяснение считаются ошибкой ответа — 502 без сохранения. Пустой выбор/отказ модели — 422, не успешный пустой образ. Recommendation проверяет ответ провайдера; wardrobe независимо проверяет membership, уникальность и непустой результат до записи.

Объяснение сохраняется в той же транзакции, что образ, состав и погода. Создание, список и карточка возвращают сохранённый текст; интерфейс не интерпретирует его как HTML или Markdown. У прежних и ручных образов поле отсутствует в JSON. Повтор с прежним `Idempotency-Key` возвращает исходный ответ: без дополнения объяснения и нового обращения к AI, даже после изменения промпта.

При первоначальном добавлении объяснения сначала разворачивается wardrobe, затем recommendation. Новый wardrobe временно принимает старый ответ `{"itemIds":[12,34]}` без объяснения; явно переданное некорректное поле не игнорируется. Новый recommendation всегда требует объяснение у модели. Старый wardrobe отвергает расширенный ответ, поэтому обратный порядок обновления не поддерживается. Откат wardrobe к прежней версии после сохранения новых ответов требует отдельной проверки совместимости.

| Ответ recommendation | Внешний результат AI-сценария |
|---|---|
| 400 invalid_request: некорректный внутренний запрос | 502: ошибка взаимодействия; пользовательские данные wardrobe валидирует до вызова |
| 422 no_outfit | 422 |
| 502 invalid_response: неверный ответ AI или поток без успешного завершения | 502 |
| 503 unavailable: нет подключения/настроек, провайдер недоступен или исчерпан лимит | 503 |
| 504 timeout: истёк срок вызова AI | 504 |

Внутреннее тело ошибки — `{"code":"..."}`; внешнее тело перечисленных AI-ошибок остаётся пустым. Некорректный ответ/неожиданный статус recommendation →502, сетевой сбой или открытый Circuit Breaker →503, таймаут Feign →504. Ошибка не запускает сохранение.

Доступность подключения проверяет recommendation при подборе, после подготовки данных и чтения S3 в wardrobe. Отдельного предварительного запроса доступности нет: ошибка входных данных или S3 может быть возвращена раньше 503 от recommendation. Отсутствие подключения не блокирует запуск сервисов и ручную работу с гардеробом.

Таймаут провайдера — 60 секунд. Feign ждёт соединения до 5 секунд, чтения — до 90 секунд; это сетевые таймауты, а не общий срок сценария. В wardrobe отключён дополнительный пул потоков Resilience4j: Feign выполняется на вызывающем worker, а дополнительный TimeLimiter не применяется. Поэтому отмена подписки не освобождает AI-слот, пока блокирующий вызов фактически не завершится. Отказ `no_outfit` не учитывается как сбой Circuit Breaker. Повторы и HTTP-перенаправления при вызове recommendation отключены.

Gateway ограничивает соединение пятью секундами, но не задаёт response timeout; общего дедлайна всего AI-сценария нет. Фильтр Retry не подключён. Сохранено стандартное поведение Reactor Netty: одна повторная попытка при сбросе соединения до отправки запроса. Если заголовки уже отмечены как отправленные, этот механизм повтор не выполняет.

### Замена части образа

`POST /api/outfits/{id}/ai-replacements` создаёт новый AI-образ. Тело содержит `name` (непустое, до300 символов), `replaceItemIds` и необязательный `candidateItemIds`. Заменяемые ID должны быть различными положительными числами из исходного состава. Исходный образ должен принадлежать подключённому USER; источник USER/STYLIST/AI значения не имеет. Погода, повод и стиль наследуются, название задаётся заново. Исходный образ и его оценки не меняются.

Все неотмеченные вещи обязательны в новом образе, заменяемые исключаются из подбора. Без списка кандидатов используется гардероб; явные ID сначала проверяются на принадлежность владельцу (чужой/несуществующий →404), затем из них исключаются заменяемые. Сохраняемые вещи добавляются автоматически. Кандидаты без фото пропускаются, но отсутствие фото у сохраняемой вещи даёт400.

Сохраняемые вещи и кандидаты вместе — максимум20, включая хотя бы одну новую вещь. При превышении или отсутствии нового кандидата —400 до S3. Автоматическая SQL-выборка исключает заменяемые до применения лимита; набор не усекается. Обычный подбор и замена используют общий AI-слот.

Wardrobe передаёт в recommendation дополнительное `requiredItemIds`: список сохраняемых ID, пустой при замене всего состава. Для обычного подбора поле отсутствует. Recommendation проверяет ID и передаёт их модели как данные. Оба сервиса проверяют, что результат включает все обязательные вещи и хотя бы одну новую; нарушение →502 без сохранения. Пустой результат модели по-прежнему даёт422.

Успех —201, `OutfitResponse` и `Location: /api/outfits/{id}` нового образа. Если исходный образ удалён во время подбора, финальная проверка под блокировкой возвращает409. Существующие проверки фотографий, прав, атомарность и правила `Idempotency-Key` сохраняются. Сначала обновляются промпт и recommendation, затем wardrobe; повторного запроса без обязательных ID при несовместимости нет.

В собственной карточке USER доступна форма замены. Пользователь отмечает исходные вещи и выбирает кандидатов вручную либо оставляет весь гардероб. Неотмеченные вещи сохраняются автоматически. После успеха открывается новая карточка; ошибка сохраняет ввод. Повтор использует прежний ключ, а «Новая попытка» требует подтверждения возможного повторного расхода AI-квоты. В клиентском и административном просмотре формы нет.

### Общий конвейер подбора

1. Проверить текущего пользователя и допуск к личному AI, данные запроса; занять единственный слот подбора до загрузки фото. При занятости —503, без очереди, S3 и AI.
2. Нет/null candidateItemIds — весь гардероб; явный список — различные положительные ID без null. Чужой/несуществующий ID →404. Исключить вещи без фото; после фильтрации должно остаться 1–20. Берётся фото с наименьшим ID. Не вводить новый лимит длины исходного явного списка.
3. Прочитать кандидатов, погоду и профиль владельца короткой транзакцией; получить фото из S3 с проверками активности до/после и повторной проверкой метаданных. Исчезнувшее исходное фото →409.
4. Ещё раз проверить активность перед вызовом recommendation. Получить и проверить выбранные ID и объяснение; выполнить финальную проверку account перед транзакцией.
5. Одной локальной транзакцией заблокировать все исходные вещи, проверить все использованные photoId, создать образ с объяснением, состав и погоду. Исчезнувшие вещь/фото →409. Вернуть 201, OutfitResponse и Location: /api/outfits/{id}.
6. Освободить слот при успехе и при любой ошибке. При отмене запроса слот остаётся занят до завершения фактически выполняющегося сценария, а не только до отключения HTTP-клиента.

Максимум исходных фото — 200 000 000 байт на подбор. Base64 для двадцати максимальных файлов занимает 266 666 720 байт плюс JSON и характеристики; внутренний транспорт и JSON-парсер должны принимать существующий максимум, включая одну строку imageBase64 длиной 13 333 336 символов. Новый суммарный лимит 20 МБ, уменьшение изображений или отправка только части кандидатов не вводятся. Размер до вызова AI и единственный слот ограничивают подготовку, но не доказывают достаточность памяти процесса.

Ошибки подготовки/проверки/AI до сохранения не создают образ. Ошибка БД откатывает всю транзакцию. При наличии Idempotency-Key захват команды или возврат сохранённого ответа предшествует занятию AI-слота; сохранение ответа входит в транзакцию образа. Потеря HTTP-ответа допускает безопасный повтор с тем же ключом по правилам выше; без ключа исход может остаться неизвестным.

## Сценарии приёмки

Сценарии покрываются JUnit/Mockito и Testcontainers-тестами с given/when/then и JDBC-фикстурами. Результаты полного прогона и проверки Compose приведены в [acceptance.md](acceptance.md).

| Сценарий | Ожидаемый результат |
|---|---|
| Внешние пути через Gateway | Прежние методы/DTO/статусы, multipart, Location и X-Total-Count; вложенные admin/stylist ресурсы попадают в wardrobe |
| Внутренний/неизвестный API через Gateway | 404, без утечки endpoint и без HTML fallback |
| Account недоступен/таймаут/невалидный ответ | 503; нет записи, выдачи фото или разрешающего fallback |
| Отзыв до финальной проверки | Операция запрещена по правилам сценария; записи нет |
| Отзыв после проверки, в том числе во время ожидания блокировки | Операция может завершиться; следующий запрос доступа отвергается |
| Администратор и BLOCKED-владелец | Модерация разрешена ACTIVE ADMIN; блокировка/смена роли администратора до проверки запрещает её |
| Отзыв/блокировка замечены повторной проверкой после S3 | Байты не выдаются; ошибка по правилам доступа. Для AI потеря активности/роли →403, технический сбой account →503. Более поздний отзыв не гарантирует отмену передачи |
| Метаданные фото удалены во время скачивания | Байты не выдаются: скачивание →404, AI-подбор →409 из-за изменения исходных данных |
| Занятый AI | 503 до S3 и recommendation; после завершения/ошибки новый подбор доступен |
| Максимальный допустимый набор изображений | Принимается внутренним HTTP/JSON-транспортом без скрытого меньшего лимита; тест с заглушкой, не платным AI |
| Отказ/неверный/незавершённый ответ AI или таймаут | Согласованная ошибка, образ не записан, нет автоматического повтора |
| Вещь или фото удалены во время подбора | 409 до создания образа; проверяются все исходные кандидаты, не только выбранные |
| Ошибка записи состава/погоды/истории | Полный rollback соответствующей локальной операции |
| Лимит фото и конкурентные загрузки | Предварительное превышение без S3 PUT; под блокировкой сохраняется максимум пять метаданных |
| Изменение/отмена оценки, удаление образа | Версии и история сохранены; удаляются текущие оценки, не история |
| Реактивный HTTP-путь | JDBC-транзакция целиком на одном worker-потоке; внешние вызовы вне транзакции, блокирующая работа вне event loop |
